# 现状、需求与设计细则

在第零、第一或第二步需要具体方法、字段和判定条件时读取相应章节。

## 一、现状盘点

### 1. 盘点对象及问题

| 对象 | 需要回答的问题 |
| --- | --- |
| 业务与资料 | 哪些规则、流程、样例和外部约束仍然有效？ |
| 产品与技术资产 | 哪些原型、代码、数据、接口和组件可以复用，运行状态如何？ |
| 团队能力 | 谁负责需求、设计、开发、测试和验收，关键技能是否有缺口？ |
| 工程设施 | 仓库、环境、数据库、存储、部署、监控和持续集成是否具备？ |
| 外部资源 | 平台、模型、账号、授权、额度和预算条件是什么？ |

### 2. 三级证据状态

- **存在**：有文件、代码、账号或文档记录；
- **可用**：已经实际运行或验证过；
- **可承诺**：能力、授权、成本和稳定性足以进入交付范围。

“盘上存在代码”不能推导出“能力已经可用”，“接口调用成功一次”也不能推导出“可以纳入交付承诺”。

### 3. 五种盘点方法

1. **事实清单法**：建立与当前判断有关的资产、人员、环境和资源索引；只对影响复用和选型的关键项做运行、构建、探活或访谈，不一开始全量测试。
2. **证据标记法**：事实能定位到文件、运行结果、配置或责任人；推断写明依据和反证条件；无法静态确认的登记验证。
3. **复用边界法**：明确复用的是代码片段、结构、数据模型还是运行能力，同时列出目标差异。能读取代码不等于能继承业务模型。
4. **能力访谈法**：团队区分“做过、能独立交付、能负责验收”，确认实际经验、投入程度、评审能力和岗位备份；环境区分本机可运行、团队可复现和生产可使用。
5. **风险抽样法**：优先验证会改变路线的未知数；只读核验与产生费用、写入或外部影响的核验分别授权。

现状基线说明现在有什么；需求基线说明决定做什么；方案说明决定怎么做；当前批次说明本次具体交付什么，四者不能混用。

## 二、需求梳理与统一语言

### 1. 轻量统一语言

| 字段 | 要求 |
| --- | --- |
| 规范名称 | 后续统一使用哪个词 |
| 简短定义 | 概念是什么，不描述系统实现 |
| 非等价词 | 哪些近义词不能混用 |
| 边界与反例 | 什么不属于这个概念 |
| 当前状态 | 已确认、暂定或存在冲突 |

术语一经澄清立即记录，不等讨论结束统一整理。用具体场景检验边界，例如“完成”指生成成功、用户采纳还是业务定稿，“保存”指暂存、文件落盘还是正式入库。

资料或代码能回答的问题先自行查证。口头描述与代码行为不一致时，区分“当前实现如此”和“目标业务应当如此”，不能由其中一方自动覆盖另一方。

### 2. 需求三维判断

- **重要程度**：核心、非核心或明确不做；
- **明确程度**：已经想清楚或仍有歧义；
- **确认方式**：讨论可确定，或必须依赖调研、测试和外部条件。

目标、规则和优先级不清时向业务方提问；外部能力不清时登记验证，不用讨论代替验证。暂时不能确认但不影响整体设计的，可带假设推进；影响核心范围的，暂停相关设计。

### 3. 六种需求方法

1. **决策树访谈**：先给出问题全貌和决策主干请对方校正，再展开前置条件已明确的问题。每题给出建议、选项和代价，事实先自行查证；分点完成后先汇总整体理解，再写入基线。
2. **场景推演**：一次验证一个真实问题，从高频主链路沿“触发—输入—业务对象—责任动作—结果—异常恢复”走查。没有业务依据的低频分支只登记，不展开。
3. **边界追问**：用正例、反例和极端情况澄清从何时开始不算、失败后算什么、重复操作怎么办、谁有权推进和是否允许后补。
4. **责任分离**：对关键动作确认谁提出、谁决定、谁执行、谁留痕，不让普通消息或系统返回结果替代明确的业务动作。
5. **反向排除**：区分当前阶段不做与永久不需要，避免后续专项被误删或提前塞入本期。
6. **编号追溯与冻结检查**：编号发布后不因排序变化重排；冻结前集中处理核心口径、范围、指标和验收影响，普通页面细节不阻塞整体基线。

## 三、方案设计

统一语言在本步发展为领域模型：术语回答“在说什么”，概念关系回答“如何关联”，领域模型回答“对象如何构成业务”，接口与数据模型回答“系统如何交换和保存事实”。

领域模型至少明确核心实体及身份、关系与边界、生命周期与状态转换、创建和修改责任、必须长期保存的事实，以及不同上下文如何引用。

### 1. 业务事实优先

从业务动作反推必须保存的对象、关系、输入快照、操作人和结果。页面是事实的视图，不为每个页面复制状态。

### 2. 交互策略与布局决策

涉及界面时，先检查已有页面、原型、截图、设计系统、组件规范和典型任务，提取明确原则与实际惯例，分别标注**可继承依据、存疑做法和明确反模式**，注明来源。现状是证据，不是设计正确性的证明；无法判断某项做法是业务约束还是历史偶然时，先追溯来源，仍不能确认再提问。

先回答用户的主要任务、工作频率、全局概览需求、比较与反复切换、并行处理和中断恢复，再明确主对象、主操作、核心状态及常驻与按需展开的信息。据此选择工作台、列表—详情、主从视图、编辑器、看板或向导等产品形态，再选择组件。

**流程描述业务推进关系，不直接决定页面结构。**步骤数量、工作项数量和后台处理阶段都不是页面分区依据。只有顺序严格、上下文少且需要明确引导时才考虑向导；需要跨阶段理解、比较或反复切换时，优先论证整体工作区、列表—详情等非步骤式结构。卡片只用于确有必要的并列摘要、独立实体或离散操作入口。

不泛泛询问“设计原则是什么”，先给出有依据的推荐、备选和代价。以下情况必须请用户确认：现有前端与任务目标冲突；现有依据缺失或相互矛盾；存在多种高影响产品形态；需要改变整体导航、核心操作习惯或视觉方向。局部组件、间距和常规样式按已确认规范默认推进。用户要求保留存疑现状时，记录约束及代价，不将其写成合理设计原则。

在《产品交互方案》中增加“交互原则与布局决策”一节，记录设计依据、核心任务、选定形态及原因、信息层级、主操作路径、关键取舍和明确避免的模式，不另建长文档。

### 3. 状态机与故障矩阵

对核心对象列出推进、失败、超时、取消、重试和迟到结果；对外部依赖列出不可用、重复响应、部分成功、限额和恢复方式。逐格确定允许行为和用户可见反馈。

### 4. 风险驱动设计

优先做深身份权限、核心标识、事务并发、文件生命周期、外部副作用和恢复路径；普通展示和非关键字段后补。区分必须现在确定的约束与可以替换的组件。

### 5. 适配边界与降级

外部服务通过稳定接口接入，定义正常、降级和失败关闭路径。未经验证的能力不进入核心承诺，不用静态结果或假状态冒充真实成功。

### 6. 多线交叉走查

用同一业务场景贯通流程、领域、交互和技术。冲突先登记位置和影响，再裁决并同步修改，不直接采用“最新修改版本”。

### 7. 现成优先与最小实现

优先复用经过验证的成熟能力，自研集中于真正有业务差异的部分；记录版本兼容、供应商锁定和替换成本。只建设当前范围和必要衔接，不为想象中的未来提前搭平台。

### 8. 核心契约先行

方案阶段明确核心业务语义、权限、状态、幂等、事务和恢复；普通字段、完整请求响应、索引和迁移细节可在对应工作项开工前补齐。

接口设计定义外部如何读取和改变事实；数据库设计定义事实如何可靠保存。机器可读契约可由 OpenAPI、Schema 和迁移文件承载，Markdown 解释业务语义和约束，避免重复所有字段定义。
