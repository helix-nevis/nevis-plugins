# 审计与验证细则

第三步需要执行具体审查、证据卡或短探针时读取。本文件不授权任何有费用、真实数据、外部写入或生产影响的验证。

## 一、三个审计对象

1. **方案内部是否自洽**：业务、产品、交互和技术描述是否一致，是否存在状态缺失、流程断点或无法落地的承诺。
2. **需求是否完整覆盖**：不仅看文档是否提到，还要确认流程、交互、技术和验收入口如何实现。
3. **是否具备规划条件**：哪些工作可以拆解，哪些仍等待决策、验证或补充。

## 二、问题分类与分级

| 类型 | 处理方式 |
| --- | --- |
| 设计类 | 进入统一待决项，由责任人决定 |
| 证据类 | 进入验证事项，通过资料、原型、测试或真实环境解决 |
| 规划类 | 在工作拆解时补充，不影响整体方案的可延后 |

按影响分为阻断、局部回填和后续登记。阻断问题关闭前不得实施相关工作；局部问题明确回填；纯优化和未来事项登记。

完成条件是问题已经解决或有明确处理安排，不是会议已经召开。

## 三、双向追溯与反例

正向逐条检查需求是否有流程、交互、技术和验收入口；反向检查关键方案是否追溯到需求或明确决策，既防需求遗漏，也防无意新增业务。

围绕以下情况构造反例：

- 重复提交；
- 并发推进；
- 迟到结果；
- 部分失败；
- 权限越界；
- 数据恢复；
- 外部限额。

审查重点是业务事实是否会被覆盖、伪造或错误推进，而不只是正常路径能否演示。

## 四、证据卡

每个验证事项明确：

| 字段 | 说明 |
| --- | --- |
| 验证对象 | 哪个平台、模型、路线或能力 |
| 环境 | 使用的数据库、浏览器、设备、账号或服务条件 |
| 输入 | 必要数据、配置及其脱敏边界 |
| 步骤 | 可复核的操作或测试步骤 |
| 完成证据 | 什么结果才算完成 |
| 限制 | 未覆盖范围和环境差异 |
| 结论 | 通过、部分通过、不通过或尚不能判断 |

一个成功案例不能代替整组能力；“部分通过”必须列出未通过范围。证据进入证据层，重要结论再按权限回填正文。

## 五、短探针

可能推翻核心方案的未知，不等完整审计结束才处理。短探针必须：

- 只回答一个关键未知；
- 限定问题、成本、输入、时长和停止条件；
- 先判断只读探针是否足够；
- 有费用、真实数据、外部写入或生产影响时单独授权；
- 保存证据、环境、限制和结论；
- 将影响当前方案的重要结论回填权威正文。

## 六、默认通过与异常升级

常规一致性和覆盖检查由智能体完成，不要求人工逐项打勾。只向责任人提交：

- 实质矛盾；
- 缺失的关键证据；
- 重大方案取舍；
- 阻断实施或不可规划事项。

审查与决策分离：审查者可以判断“不一致、缺证据、不可开工”，不能自行改变业务目标、核心范围、重大技术路线或验收承诺。审计记录不另起一套方案正文。
