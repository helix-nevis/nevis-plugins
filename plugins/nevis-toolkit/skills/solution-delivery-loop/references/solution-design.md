# 方案设计细则


### 设计入口与协同推进

先引用需求文档及有效基线、独立统一语言、业务流程、项目档案和现状资产索引，明确本轮设计范围与排除项。按当前问题读取相关内容，不把建档重做一遍。业务流程独立于拟建工具，关键活动须说明目的、所需信息、核心关注、角色责任、结果及异常，不能仅用箭头代替。

在方案概述中提取设计驱动因素，不另建重复参数文件：

| 驱动因素 | 需要明确的内容 |
| --- | --- |
| 硬性约束 | 必须满足什么，引用具体上游依据 |
| 关键质量要求 | 时效、性能、可靠性、可追溯性等如何影响当前设计 |
| 系统与集成边界 | 外部角色、系统、数据源与服务分别承担什么责任 |
| 规模与使用条件 | 用户、数据、并发、部署和维护条件；区分事实与规模假设 |
| 关键取舍 | 当前真实存在的目标冲突、代价及影响 |
| 关键未知 | 可能推翻方案的问题，调查或验证安排及阻塞范围 |

需求不完整时可以做候选推演或技术调查，但必须标明假设，不形成确定承诺；必要澄清只阻塞依赖它的设计，其他部分可继续。已有有效答案不重复问，不逐项询问抽象质量偏好。影响目标、核心操作、公共契约、成本、部署或维护方式的重大取舍，先给依据、候选和代价，再用 AskUserQuestion 确认；普通选择由智能体推进。

按“设计依据 → 核心场景 → 协同设计 → 调查、验证或提问 → 场景回检 → 整理有效结论”循环，不固定先完成全部技术栈、再架构、最后才设计用户操作。

| 设计视图 | 核心内容 |
| --- | --- |
| 领域与业务状态 | 对象身份、关系、责任、规则、生命周期、状态与长期事实 |
| 产品与操作流程 | 产品形态、信息层级、入口、动作、自动行为、反馈、结果与恢复 |
| 系统架构与实现路径 | 系统边界、子系统与模块职责、协作、处理路径、状态归属与部署 |
| 数据与接口契约 | 保存的事实、数据关系与存储分布，边界输入输出及行为语义 |

四个视图围绕同一场景按依赖细化，分别引用需求，关键选择说明依据；不是四份文档各自写完就视为整体成立。适用范围很小时可合并表达，没有人机操作的内部服务可省略界面部分，仍保留调用和反馈契约。

### 需求、交互与技术的衔接

需求明确用户任务、业务行为、规则、质量和可观察结果；交互设计明确入口、页面、操作路径、反馈及异常恢复；技术方案说明系统边界与职责、架构和部署、技术选择、数据与接口契约，并描述为实现这些要求所需的内部处理路径。实现路径是技术方案的一部分，不是与技术方案并列的产物，也不等同于完整技术方案。技术可行性调查可以提前，但不能替业务方决定规则。数据新鲜度与历史追溯属于需求，更新调度、数据处理与存储机制属于技术方案中的实现路径；分析结果的质量要求不自动等于必须采用 AI。

交互方案引用需求项及现有界面依据，对照已满足、部分满足、缺失、冲突和无需求依据的行为，决定继承、调整或新增。现有按钮和字段不自动成为必须保留的需求；发现遗漏时回到需求梳理，不由设计者静默补定。业务功能分组不等于技术模块或交付工作项，一项需求可跨多个模块，一个模块也可支持多项需求。

统一语言在本步发展为领域模型：术语回答“在说什么”，概念关系回答“如何关联”，领域模型回答“对象如何构成业务”，接口与数据模型回答“系统如何交换和保存事实”。

领域模型至少明确核心实体及身份、关系与边界、生命周期与状态转换、创建和修改责任、必须长期保存的事实，以及不同上下文如何引用。

### 1. 业务事实优先

从业务动作反推必须保存的对象、关系、输入快照、操作人和结果。页面是事实的视图，不为每个页面复制状态。先区分核心对象及其关系，再选择统一或分离的实现模型；业务语义未对齐时不得先比较表结构和存储方案。

命令、按钮、任务、事件和快照都隐含业务时点及责任，必须追溯到已确认场景。输入快照、幂等、版本和并发机制服务于该业务时点，不得反过来决定用户如何操作。

### 2. 交互策略与布局决策

涉及界面时，先检查已有页面、原型、截图、设计系统、组件规范和典型任务，提取明确原则与实际惯例，分别标注**可继承依据、存疑做法和明确反模式**，注明来源。现状是证据，不是设计正确性的证明；无法判断某项做法是业务约束还是历史偶然时，先追溯来源，仍不能确认再提问。

先回答用户的主要任务、工作频率、全局概览需求、比较与反复切换、并行处理和中断恢复，再明确主对象、主操作、核心状态及常驻与按需展开的信息。据此选择工作台、列表—详情、主从视图、编辑器、看板或向导等产品形态，再选择组件。

**流程描述业务推进关系，不直接决定页面结构。**步骤数量、工作项数量和后台处理阶段都不是页面分区依据。只有顺序严格、上下文少且需要明确引导时才考虑向导；需要跨阶段理解、比较或反复切换时，优先论证整体工作区、列表—详情等非步骤式结构。卡片只用于确有必要的并列摘要、独立实体或离散操作入口。

不泛泛询问“设计原则是什么”，先给出有依据的推荐、备选和代价。以下情况必须请用户确认：现有前端与任务目标冲突；现有依据缺失或相互矛盾；存在多种高影响产品形态；需要改变整体导航、核心操作习惯或视觉方向。局部组件、间距和常规样式按已确认规范默认推进。用户要求保留存疑现状时，记录约束及代价，不将其写成合理设计原则。

在《产品交互方案》中增加“交互原则与布局决策”一节，记录设计依据、核心任务、选定形态及原因、信息层级、主操作路径、关键取舍和明确避免的模式，不另建长文档。

### 3. 页面功能与真实链路设计

关键页面功能逐项说明用户目的、数据来源、时间与业务口径、处理责任、需要长期保存的事实、接口返回、输出结果、刷新方式和异常。区分业务规则与技术实现，不能只写“调用接口”或“生成内容”；数据不完整、结果能否追溯、保存与重新生成规则必须有明确位置。

关键按钮先定义业务动作，再定义请求：创建什么对象、携带哪些必要上下文、生成草稿还是正式结果、谁可修改与确认、同步或异步、重复操作、失败恢复、离开后继续和权限如何处理。不能用“点击后调用接口”替代这些判断。

现有前端重构时，页面通过接口层与后端和样例数据隔离，假数据不得散落组件或冒充真实成功。组件、全局样式令牌、路由和状态管理按真实复用与一致性需要提取，不为组件化过度拆分；已确认的行为由测试或必要基线保护。

### 操作流程的完整表达

每条核心操作流程说明入口与前提、用户可见信息、输入与动作、系统自动行为、加载与成功反馈、空结果与失败反馈、最终业务结果，以及取消、重复操作、中断和恢复。步骤列表可辅助表达，但不能只有点击顺序；一个业务活动可有多种操作流程，一次操作也可支撑多个业务活动。

CLI 同样需要设计输入、输出和恢复，不因没有图形界面跳过交互。按本轮需求及必要衔接覆盖流程，不只按优先级标签选择。已有视觉规范优先引用；缺少依据且影响整体形态或使用习惯时才确认方向，不强制画完整原型，必要时引用线框或原型文件。

### 系统架构与技术取舍

架构分别说明逻辑职责、运行进程与部署单元，图中标明边界类型，不把子系统、模块、服务与进程混作同一层次。每个主要单元说明做什么、不做什么、承接哪些需求、与谁协作；代码位置仅在已有或确需确定时引用，不用目录划分代替职责设计。

用核心场景说明实现路径：输入从哪里来、由哪个系统职责处理、发生何种转换或分析、产生并保存什么业务事实、如何返回或通知，以及超时、错误、部分失败、重试和恢复如何处理。说明关键处理责任、输入输出与必要状态，不要求展开普通内部函数。明确持久业务事实、运行时状态和配置的持有者、修改责任及故障恢复方式；逻辑、通信与部署视图保持一致。

技术方案是设计产物，实现路径是其中描述信息处理与协作过程的部分；技术方案还包括系统及子系统边界、模块职责、技术选择、部署、状态归属和数据接口契约。不要将二者并列为重复产物。

故障恢复说明系统如何处理错误、部分成功、重试与数据恢复；操作流程中的中断恢复说明用户取消、离开或重新进入后如何继续。关键故障场景应说明两者如何衔接，避免把后台重试写成用户操作，或把用户操作提示误写成系统恢复机制。

技术选型以设计驱动因素为标准，先核对既有技术与可复用能力；对有真实取舍的关键路线比较候选，记录推荐、排除理由、适用条件、证据和待验证部分，必要时给替代路径。常规成熟依赖不为凑数强列候选，不逐维度审批；不设固定组件数量上限，也不将单体、前后端分离、事件驱动、管道当作同一维度的互斥模式。技术性能、成本和兼容结论须有适配条件的资料或验证依据，不能用流行度、示例数字和技术印象定案。

### 4. 状态机与故障矩阵

对核心对象列出推进、失败、超时、取消、重试和迟到结果；对外部依赖列出不可用、重复响应、部分成功、限额和恢复方式。逐格确定允许行为和用户可见反馈。

### 5. 风险驱动设计

优先做深身份权限、核心标识、事务并发、文件生命周期、外部副作用和恢复路径；普通展示和非关键字段后补。区分必须现在确定的约束与可以替换的组件。风险在设计全程发现并复用统一事项记录，说明具体未知或触发条件、影响的需求与设计、已有及缺少的证据、缓解或验证安排、剩余风险和阻塞范围；只记实际相关项，不为完整性堆砌通用风险。

### 6. 适配边界与降级

外部服务通过稳定接口接入，定义正常、降级和失败关闭路径。未经验证的能力不进入核心承诺，不用静态结果或假状态冒充真实成功。

### 7. 多线交叉走查

用同一业务场景贯通流程、领域、交互和技术。冲突先登记位置和影响，再裁决并同步修改，不直接采用“最新修改版本”。

### 8. 现成优先与最小实现

优先复用经过验证的成熟能力，自研集中于真正有业务差异的部分；记录版本兼容、供应商锁定和替换成本。只建设当前范围和必要衔接，不为想象中的未来提前搭平台。

### 9. 核心契约先行

方案阶段明确核心业务语义、责任、权限、状态、幂等、事务和恢复；优先覆盖前后端、跨模块协作、并行开发和外部集成边界，说明调用方向、输入、输出、错误与相关行为条件。先有领域语义，再决定持久化，不由名词直接推导表结构。普通字段、完整请求响应、索引和迁移细节可在对应工作项开工前补齐，但不能在必要协作契约缺失时开始相关实现。

接口设计定义外部如何读取和改变事实；数据库设计定义事实如何可靠保存。机器可读契约可由 OpenAPI、Schema 和迁移文件承载，Markdown 解释业务语义和约束，避免重复所有字段定义。

### 设计自检与交接

整理当前有效方案与阅读入口：本轮范围、上游依据、驱动因素、各视图位置、关键决策、证据及未决影响。先检查当前需求是否有设计支撑、同一场景四视图是否一致、核心操作与对象责任状态是否明确、架构通信是否具备必要契约、关键路线是否有依据或验证安排。阻断项解决或隔离后再交独立审计，其他待定说明安排，不以 TODO 全部清零或文档齐全作为完成标准。

不默认另造汇总 YAML；有真实机器消费者时才定义结构化契约，指定权威位置，其他正文引用而不维护重复口径。设计自检不代替第三步独立审计，设计确认不等于规划通过或开工授权。
