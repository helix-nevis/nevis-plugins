# 需求梳理与统一语言细则


### 1. 来源与调查循环

来源包括用户当前输入、文档、现有界面（原型、截图或实际系统）和对话历史。代码、接口、样例数据与验证记录是解释现状和核对约束的辅助证据。来源中要区分目标、诉求、当前做法、业务规则、方案建议、技术实现与隐含假设；现有界面只说明当前怎么做，历史讨论中的候选不自动成为当前结论。

按以下循环推进，不一次提取后整组确认：

1. 从盘点索引定位相关资料，整体理解目标、角色、场景与业务流，形成有出处的候选诉求。
2. 建立持续的需求调查问题清单，检查谁在什么情境下做什么、输入如何取得、责任与规则、结果、异常及完成判断。
3. 带着问题定向查阅材料，找到答案就记录结论与具体出处，不无目的通读。
4. 查不到、来源冲突或必须由业务方取舍时，用 AskUserQuestion 少量分批提问；已有答案不重复问。
5. 根据答案补充新问题，继续调查、推演与澄清，不能将启发型问题自动升级为新增需求。
6. 回到整体业务流校验遗漏、矛盾、关键默认值与用户负担，整理诉求并转译为需求文档，对核心范围和关键取舍作必要确认。

问题分澄清型（歧义与边界）、启发型（遗漏与反例）、确认型（关键取舍）；复用统一事项清单，不另建重复问答台账。只保存问题、关联诉求或场景、结论及来源、状态与影响、回填位置，不复制全部问答。影响当前核心范围和基线的问题须解决、排除或明确隔离受影响范围；其他问题说明安排，不要求全量清零，也不能只登记就绕过阻断。关闭后回填诉求、统一语言或需求正文。

### 2. 诉求转译与需求表达

客户诉求清单保留用户意图及澄清、处置结果，需求文档组织当前业务要求，统一语言独立维护共享语义。需求项引用诉求项，诉求项引用具体消息、文档章节或界面位置；法规、外部契约与明确约束可直接成为需求依据，不虚构客户诉求。

表达不同而意图相同的诉求可合并并保留多源；一条诉求可拆成多项需求，多条诉求也可支撑同一需求。保留不采纳、暂缓、否定或替代的必要原因，不静默删除。确认状态、重要程度和本期是否纳入分别表达；核心性、优先级和迭代不能绑定。

功能需求表达骨架：**在什么场景下，哪个角色需要系统提供什么行为，遵守什么规则，得到什么可观察结果。**至少有稳定编号、名称、描述、依据与验收；规则、边界、异常和质量要求按实际需要补充或引用。避免“正常运行”等不可判定验收，不强迫每条需求套长表。

例如：FR-012 查看趋势简报——店主准备企划时，可以查看所选市场与时间范围的简报，识别覆盖期与更新时间并追溯关键结论的依据；无符合条件的内容时明确告知。引用对应诉求与约束，以范围、新鲜度和依据可识别作为验收点；允许延迟多久未确定时，保留具体问题，不自行填写数值。

按业务能力或功能域分组，层级按复杂度展开，不强凑四级，不默认新增与需求重复的功能编号。成本或可行性信号仅标记具体未知及影响，不据技术名词推定工作量；统计、报价和复用系数不是通用必填项。

### 3. 轻量统一语言

| 字段 | 要求 |
| --- | --- |
| 规范名称 | 后续统一使用哪个词 |
| 简短定义 | 概念是什么，不描述系统实现 |
| 非等价词 | 哪些近义词不能混用 |
| 边界与反例 | 什么不属于这个概念 |
| 当前状态 | 已确认、暂定或存在冲突 |

术语一经澄清立即记录，不等讨论结束统一整理。用具体场景检验边界，例如“完成”指生成成功、用户采纳还是业务定稿，“保存”指暂存、文件落盘还是正式入库。

资料或代码能回答的问题先自行查证。口头描述与代码行为不一致时，区分“当前实现如此”和“目标业务应当如此”，不能由其中一方自动覆盖另一方。

### 4. 从信息到候选需求

先区分业务目标、用户任务、业务规则、当前做法、方案建议、技术实现、隐含假设和待决与待验证事项，保留出处。文档写了、代码存在或行业常见都不能单独证明需求成立；“做一个卡片”是方案候选，“用户据此识别问题并完成判断”才可能是需求。

按“事实地图—核心角色与高价值主线—场景合并证据—候选需求—内部推演—整体基线”推进。同一需求可能分散在文档、原型、代码和会议记录中，先跨来源组合，再检查来源、冲突、角色、对象、条件、结果、用户负担、反例和替代方案。详细扫描由智能体完成，不把每个小问题都抛给用户。

登录、身份识别、组织归属、权限、角色和进入条件属于需求，不是可默认套用的技术设施。凡要求用户提供内部标识、额外信息、专业知识或前置准备，先判断用户如何获得、是否必要、系统能否自动取得，以及是否有更低负担且不改变业务结果的替代方案。关键默认值未确认时不得作为基线进入开发。

### 5. 需求三维判断

- **重要程度**：核心、非核心或明确不做；
- **明确程度**：已经想清楚或仍有歧义；
- **确认方式**：讨论可确定，或必须依赖调研、测试和外部条件。

目标、规则和优先级不清时向业务方提问；外部能力不清时登记验证，不用讨论代替验证。暂时不能确认但不影响整体设计的，可带假设推进；影响核心范围的，暂停相关设计。

### 6. 六种需求方法

1. **决策树访谈**：先给出问题全貌和决策主干请对方校正，再展开前置条件已明确的问题。对核心候选需求围绕目标、真实场景、责任、边界、异常和替代方案多轮递进反问，每轮依据上轮答案继续推演，不一次抛出完整问卷，也不只重复“是否确认”。每题给出建议、选项和代价，事实先自行查证；分点完成后先汇总整体理解，再写入基线。
2. **场景推演**：一次验证一个真实问题，从高频主链路沿“触发—输入—业务对象—责任动作—结果—异常恢复”走查。先确认用户如何发起、控制和完成核心任务，再讨论实现机制。对全局入口、核心操作方式、身份权限、核心对象或主流程等高影响原则，用端到端场景和具体界面说明实际行为、影响范围与替代方案，再请求必要确认；文档写过、历史确认过或整组原则获确认，不能替代对高影响结论的有效对齐。没有业务依据的低频分支只登记，不展开。
3. **边界追问**：用正例、反例和极端情况澄清从何时开始不算、失败后算什么、重复操作怎么办、谁有权推进和是否允许后补。
4. **责任分离**：对关键动作确认谁提出、谁决定、谁执行、谁留痕，不让普通消息或系统返回结果替代明确的业务动作。
5. **反向排除**：区分当前阶段不做与永久不需要，避免后续专项被误删或提前塞入本期。
6. **编号追溯与冻结检查**：编号发布后不因排序变化重排；冻结前集中处理核心口径、范围、指标和验收影响，普通页面细节不阻塞整体基线。
