# 工作法统一语言模型

这是工作法自身的共享概念上下文，适用于建档、需求、设计、审计、规划与交付。它不同于具体项目的统一语言：本文件定义怎样理解工作法中的概念，项目统一语言定义该项目的业务概念。不得将本文件整体复制进项目术语表。

## 一、概念与边界

| 概念 | 定义 | 不等同于 |
| --- | --- | --- |
| 诉求 | 相关方表达的愿望、困难、期望或提出的办法，是待理解和澄清的原始意图 | 已确认需求；用户提出一个按钮不代表按钮方案已确定 |
| 需求 | 根据诉求、业务规则与有效约束形成的要求，说明条件、角色、行为或结果，以及必须满足的边界与质量 | 功能名称、现有实现、技术方案或开发任务 |
| 业务活动 | 业务流程中有目的、输入、责任和结果的活动单元；用于说明业务流程由什么组成 | 单个按钮、后台处理步骤或完整业务流程本身 |
| 业务流程 | 不依赖我们拟建工具和系统的业务完成过程，由业务活动及其衔接构成，描述活动目的、所需信息、核心关注、角色责任、业务结果及上下游关系 | 简单箭头顺序、页面步骤或后台处理链路 |
| 操作流程 | 业务活动落实到界面后，用户如何操作、系统如何反馈，并完成业务任务的过程 | 业务流程本身；数据采集、解析、存储等内部实现路径 |
| 实现路径 | 为满足需求而设计的系统内部处理与协作方式，包括数据接入、转换与分析、状态变化、持久化、调度、接口通信、错误处理与故障恢复 | 用户必须逐项操作的界面步骤 |
| 技术方案 | 说明系统采用何种技术与结构来支撑需求的一类设计产物，包含架构与模块边界、实现路径、技术选型、状态归属、数据和接口契约等；实现路径是其技术处理流程部分 | 与实现路径同义的单条处理流程；需求或业务流程 |
| 系统 | 为达成目标承担一组职责的整体，具有明确边界以及与外部参与者的关系 | 单个应用页面；所有业务活动的集合 |
| 子系统 | 系统内部围绕相对完整职责组织的一组能力，有清晰边界并与其他部分协作 | 必须独立部署的服务；固定层级的目录 |
| 功能 | 系统向角色或其他系统提供的一项可识别行为或能力 | 完整需求；功能名称本身不说明全部场景、规则与验收 |
| 功能域／业务能力分组 | 为理解和组织业务要求而形成的功能集合 | 已确定的子系统、技术模块或交付批次 |
| 模块 | 设计或实现中为组织代码和技术职责划分的单元；本工作法默认按此含义使用 | 页面、功能、子系统或工作项的一一对应物 |
| 工作项 | 为交付明确结果而规划的一组工作，有范围、依据、依赖与验收条件 | 产品结构、功能目录或代码模块 |
| 执行任务 | 工作项下在开工前或实施过程中拆出的具体工作 | 需要提前细化的全部未来工作 |

质量要求和约束也是需求，不一定对应独立功能。核心性、优先级、确认状态与迭代安排分别表达。上述概念按不同目的组织信息，不强行组成一棵逐层分解的树。

## 二、业务活动、业务流程与操作流程

**业务活动**是业务流程中有目的、输入、责任和结果的活动单元。分析时说明：

- **目的与必要性**：为什么需要，解决什么问题。
- **触发条件**：什么情况下开始。
- **角色与责任**：谁处理、判断、决定和交接。
- **所需信息与条件**：需要什么，信息从哪里取得。
- **核心关注与规则**：关注什么，如何判断，有哪些边界和取舍。
- **结果与完成标准**：产生什么业务结果，怎样算完成。
- **衔接与异常**：交给谁，信息不足、失败或返工时如何继续。

**业务流程**由业务活动及其衔接构成，应先讲清关键活动的目的、所需信息、关注点、责任和结果；箭头可概括顺序关系，不能代替活动说明。业务流程描述业务本身，不受拟建页面或技术实现限定。

**操作流程**说明业务活动落实到界面后，用户从哪里进入、看到什么、输入和操作什么、系统自动完成什么、如何反馈、得到什么业务结果，以及取消、失败或用户中断后如何继续。一个业务活动可有多种操作流程，一次操作也可支撑多个业务活动，不要求逐步一一对应。“打开页面”只是动作，不是完整操作流程。

## 三、实现路径与技术方案

**实现路径**描述为了满足需求，系统内部的信息和控制如何流转：输入从何处取得，由哪个职责处理，发生何种转换或分析，产生并保存什么业务事实，如何返回或通知，以及超时、错误、部分失败、重试和恢复如何处理。它可以用步骤或图表示，但每一步需标明处理责任、关键输入输出及必要状态；不要求展开普通内部函数或所有代码细节。实现路径用于说明技术处理，不作为用户操作清单。

**技术方案**是一类设计产物，说明系统用什么结构与技术支撑需求，范围可包括系统和子系统边界、模块职责、技术选型、部署、状态归属、实现路径、数据设计与接口契约。实现路径是技术方案中描述处理流程的部分，技术方案还包含路径之外的结构、选择与契约。因此两者相关但不同层级。

发生故障时，技术方案说明系统处理与恢复机制；界面上的错误反馈、用户取消和离开后恢复属于操作流程。二者需围绕同一失败场景相互衔接，不能混为同一种“恢复”。

## 四、关系与追溯

- 诉求经分析澄清形成需求；需求项引用诉求，诉求引用原始消息、文档、界面或历史对话。法规或外部契约可直接成为需求依据。
- 业务流程由业务活动及其衔接构成，用于发现并校验需求；需求规定功能、规则、质量和约束。
- 操作流程与技术方案以需求为依据；交互方案同时引用现有界面证据，明确继承、调整与新增。
- 技术方案包含实现路径以及架构、选型与契约；实现路径说明系统内部怎样处理信息，不规定用户逐步如何操作。
- 故障恢复是系统处理错误、部分失败和数据恢复的能力；操作流程中的中断恢复是用户离开、取消或重新进入后的继续方式。关键场景需同时描述系统与用户两侧行为。
- 系统可按职责组织子系统，功能由一个或多个技术模块支撑；不要求功能与模块一一对应。
- 工作项引用需求与方案，组织跨功能、模块或子系统的交付，再按需拆为执行任务。
- 下游维护对上游依据的引用，检查时反查覆盖，不强制双向手工台账。

## 五、同一例子的分层检验

| 层次 | 示例 |
| --- | --- |
| 诉求 | 希望自动整理趋势，减少每天翻网站的时间 |
| 业务活动 | 判断本次企划值得关注的趋势方向：需要目标市场、客群、季节和可信依据；关注适配性、时效性与可信度；形成采用、观察或排除的方向及理由 |
| 业务流程 | 获取并评估趋势信息 → 判断与目标客群和企划主题的适配性 → 决定采用、观察或排除，并留下业务理由 |
| 需求 | 店主能查看相关趋势，识别覆盖期和更新时间，追溯结论依据，并保留业务需要的判断结果；具体的新鲜度阈值尚待业务确认 |
| 操作流程 | 进入企划工作区，筛选趋势、查看依据、标记采用或排除，再关联到企划；说明界面反馈与用户离开后如何继续 |
| 实现路径 | 获取数据源 → 清洗和分析 → 保存结果及来源 → 提供查询；技术方案另行决定更新调度、存储和分析组件，并定义错误、重试与恢复 |
| 技术方案 | 除上述实现路径外，还说明子系统与模块职责、部署、状态归属、技术选择及数据接口契约 |
| 工作项 | 交付一个市场范围内可查阅并追溯依据的端到端能力，明确范围、依赖与验收 |

需求确定所需新鲜度、分析质量和历史追溯要求，技术方案决定调度、模型与存储机制。不得把后台处理阶段直接变成用户步骤。

## 六、上下文使用规则

插件的 SessionStart Hook 在启动、恢复、清空、压缩恢复和分叉事件中直接注入本文件全文，不调用模型、不写入项目文件。它是工作法语义上下文，不扩展用户任务或操作授权。仅复制技能、Hook 未启用或加载失败时，调用本技能后应在首次分类或判断前读取本文件；发现术语歧义且上下文缺少定义时重新读取。无需每轮重复读取，也不要只用目录中的链接假定正文已加载。

再按任务读取项目统一语言的相关章节，区分工作法概念与项目业务术语。若项目同名词含义不同，显式说明语境；重要语义冲突先澄清，不能静默覆盖项目结论。
