# 产物与生命周期细则

在执行第零至第五步时按需读取。本文件规定长期信息如何保存，不要求机械创建全部文件。

## 一、典型产物结构

建议在项目工作目录下使用 `.proj/`，先复用已有权威位置，不机械迁移或复制：

```text
.proj/
├── README.md                 # 导航、当前入口与关键缺口
├── sources/
│   ├── INDEX.md              # 来源与资产索引
│   ├── messages.sqlite3      # 已安装捕获 Hook 时自动维护
│   └── files/                # 外部原件及必要快照
├── inbox/                    # 尚未完成归类或路由的信息
├── working/                  # 草稿、分析与辅助理解材料
└── artifacts/
    └── project-profile.md    # 项目背景、有效约定及相关入口
```

这是职责结构，不要求预建全部空目录或文件。盘点按需补齐导航、项目档案与来源索引；后续需求、方案、工作规划、统一事项及交付证据在 `artifacts/` 中按需建立，已有等价位置则引用。独立 `discovery.md` 或 `technical-baseline.md` 仅在内容有独立阅读价值时拆分，短盘点结论可留在项目档案。

### 建档与资料归属

- **项目档案**保存项目身份、业务背景与目标、本轮任务、职责、有效约束及相关入口；项目长期目标、本轮完成标志和实际状态分别表达。技术、需求、环境规则已有权威位置时引用，不复制正文。
- **来源与资产索引**记录名称与类别、位置、用途线索、判断依据及重要疑点。整体声明覆盖边界与读取深度，个别深入项单独注明，不逐文件写摘要或逐条重复“未运行”。后续调查获得新证据时更新对应项。
- **sources/files/** 保存外部交付原件和确有必要的固定版本快照。既有代码、有效文档和会话原文通常保留原位置，只登记引用；原件不随分析结论改写。
- **inbox/** 只暂存未完成归类或路由的信息。已经识别的需求、冲突、待决策或待验证事项进入对应正式产物并标明状态，不能因“未确认”长期滞留 inbox；路由后清理暂存或保留指针，避免双份正文。
- **working/** 保存草稿、推演、比较和辅助材料；形成有效结论后回填正式产物，过程材料按需要归档。
- **artifacts/** 是正式维护位置，不表示所有内容都已确认；事实、候选、有效约定和未决内容应明确区分，确认时更新原位置，不靠搬文件表达确认状态。

`.proj/` 只有消息数据库时尚未完成建档；检查档案内容并增量补齐，不重置或覆盖数据库。没有捕获 Hook 时不要求手工创建数据库。Hook 仅登记来源，不做语义分类；后续实体与结论在内容侧追加来源引用，不向消息索引写业务关联。只有取得可靠定位信息时才引用具体消息编号，不编造 `capture_id`，也不为归档重复抄写会话原文。

### 需求梳理的三个产物

正式产物按需采用 `artifacts/client-needs.md`、`artifacts/ubiquitous-language.md` 和 `artifacts/requirements.md`，已有等价位置则复用；不预建空表，也不建立人工版与智能体版两套正文。“需求基线”指需求文档中已确认的有效要求，不是第四份文件。

| 产物 | 最小内容 |
| --- | --- |
| 客户诉求清单 | 稳定编号、名称、保留用户意图的描述、具体来源、澄清与处置结论、关联问题 |
| 统一语言 | 规范名称、定义、非等价词、边界与反例、当前确认状态 |
| 需求文档 | 背景与目标、角色场景、业务流程、功能需求、业务规则、质量要求、约束、范围与排除项、验收和迭代范围 |

诉求来源可有多个，指向消息、文档章节或界面位置。候选、已澄清或存在冲突等确认情况，与暂缓、不采纳、被替代等处置结果分开表达；必要时引用原话，不复制完整消息。重要程度与是否纳入本期单独记录。

需求项至少有稳定编号、名称、场景与行为描述、依据及可验证结果；复杂规则和质量要求可独立组织后引用。功能按业务能力分组，按需分层，沿用需求编号，不为相同内容再建功能编号。迭代范围引用需求编号，不逐期复制需求正文。范围外区分不属于目标、本轮不做和后续候选，并说明原因。成本统计与售前报价表不作为通用必填产物。

调查问题复用统一事项清单，可按澄清、启发、确认分类；保存问题、关联诉求或场景、结论与来源、状态与影响、回填位置。原始问答留在会话系统，不建全量问答副本，不在总结中再复制所有结论。核心阻断按影响处理，不要求全部问题清零。

### 方案的信息边界

方案概述或导航保存本轮范围、上游依据、设计驱动因素、各视图入口、关键未决与证据引用；可在现有技术方案开头维护，不强制新增文件。以下目录按内容需要产生，不预建空文件。

```text
方案/
├── 产品交互方案.md
├── 领域模型.md
├── 技术方案.md
├── 开发规范.md
├── 契约/
│   ├── 接口设计.md
│   ├── 数据库设计.md
│   └── 外部服务契约.md
├── 决策记录.md（或引用统一决策入口）
└── 验证记录/
```

小项目可以合并。工作项、接口和数据库设计不得各自复制一套业务规则。

交互原则与布局决策归入《产品交互方案》，设计系统或项目已有规范仍是其权威来源，不在工作项和审计记录中重复维护。

| 设计产物 | 权威内容 |
| --- | --- |
| 领域模型 | 对象身份、关系、责任、规则、状态和长期事实 |
| 产品交互方案 | 产品形态、操作流程、反馈恢复、现有界面对照及原型引用 |
| 技术方案 | 架构边界与职责、实现路径、状态归属、部署及选型证据 |
| 数据与接口契约 | 事实保存、存储分布、调用方向、输入输出与行为约定 |
| 开发规范 | 当前实现必须共同遵守的约定，引用已有规范 |

四个设计视图可以合并承载，各产物引用需求和独立统一语言，不复制上游正文。风险复用统一事项；不默认创建 params、独立风险台账或全量汇总 YAML。有真实机器消费者时明确结构化契约的权威位置，其他材料引用它。核心契约在设计阶段明确，详细字段在相关工作项开工前补齐；确认方案不等于全部细节已冻结或允许开工。

## 二、贯穿信息的字段与关闭规则

### 待决与验证清单

至少记录：

- 稳定编号；
- 类型：待澄清、待决策、待验证或冲突；
- 问题或假设；
- 发现来源；
- 阻塞或影响的需求、方案和工作项；
- 处理方式：人工判断、短探针或真实环境核验；
- 状态：开放、处理中、已关闭；
- 关闭后结论回填位置。

**关闭时必须把结论写回诉求、统一语言、需求、方案、契约或工作项，清单只保留指针。** 否则清单会成为第二套事实源。

### 追溯关系

下游维护对上游依据的引用：

```text
客户诉求 → 原始消息、文档、界面或历史对话
需求项 → 客户诉求或明确的法规、外部契约与约束
交互及技术方案 → 需求项
交互方案 → 现有界面与行为依据
工作项 → 需求项、方案依据
交付记录 → 工作项、验收证据
```

一项需求可承接多条诉求，一条诉求可转译为多项需求。不强制上游手工维护下游编号列表；审查时沿引用反查承接与覆盖，不把反向检查误写成双向手工台账。没有客户诉求的法规要求可直接引用依据，不虚构诉求。诉求未被承接时应有澄清或处置说明。

### 决策记录

只收难以逆转、缺少背景容易令人意外且存在真实权衡的决定。只追加，保留当时背景、选项、代价、结论和影响；普通实现修正不进入重大决策记录。

## 三、生命周期表

| 产物 | 创建时机 | 更新条件 | 收尾方式 |
| --- | --- | --- | --- |
| 项目档案 | 第零步，按需补齐 | 背景、目标、本轮任务或有效约定变化 | 保留当前有效信息及来源 |
| 来源与资产索引 | 第零步，后续按需加深 | 新来源、路由、位置变化或新增证据 | 保留导航、覆盖边界与调查入口 |
| 客户诉求清单 | 第一步，从原始来源提取 | 新诉求、澄清、冲突或处置变化 | 保留意图、出处与必要处置原因 |
| 统一语言 | 第一步，全程演进 | 概念澄清或语义变化 | 独立维护并同步受影响引用 |
| 需求文档与基线 | 第一步，诉求转译后 | 候选逐步收敛，已确认要求仅经获批变更 | 保留当前基线与必要变更记录 |
| 方案与契约 | 第二步 | 审计回填、执行偏差、外部假设被推翻 | 保留当前有效方案 |
| 待决与验证清单 | 全程 | 发现即登记，解决即关闭 | 结论回填正文，开放项保留，历史可归档 |
| 决策记录 | 按需 | 只追加 | 长期保留背景与权衡 |
| 工作规划 | 第四步 | 状态和批次变化 | 当前批次保留，历史批次归档 |
| 任务与交付记录 | 执行期 | 任务推进和关闭 | 保留证据索引，过程可归档 |
| 过程日志 | 按需 | 排查与交接需要 | 默认归档，不进入长期正文 |

## 四、归档判断

只有执行、验收、决策或变更仍依赖的内容才保留在长期阅读入口。中间讨论、失败尝试、工具调用、重复日志和已被覆盖的临时判断，可以在保留必要证据索引后归档。

归档不是删除所有历史：重大决策保留背景，交付保留证据索引，需求保留必要变更记录；但不把过程日志当作新的需求或方案正文。
