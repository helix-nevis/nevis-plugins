# 现状盘点细则


### 1. 职责与执行顺序

盘点以建立资料和能力索引为主，回答项目是什么、本轮解决什么、相关入口在哪里、已有依据到什么程度，以及下一步还需调查什么。覆盖本轮相关来源和主要区域，不要求读取全部内容或实际运行。

按“识别已有档案 → 提取当前已知信息 → 补齐最小结构 → 扫描并建立索引 → 针对缺口补问 → 更新档案与下一步入口”推进。新项目同样可以建档，没有代码时记录已有背景和资料入口，不强凑技术信息。

先复用已有权威文档，不机械迁移或复制。`.proj/` 可能只有 Hook 创建的消息数据库，不能据此认定已建档；检查项目档案及当前任务必需信息，已有则按需补充，缺失则建立，保留原有数据。目录与产物归属见[产物与生命周期细则](artifacts-and-lifecycle.md)。

### 2. 值得收集的信息

只收集会改变项目理解、执行方式或完成判断的信息；以下是按需覆盖的类别，不是初始化必填表。

| 信息组 | 收集内容与入口 |
| --- | --- |
| 项目身份与位置 | 名称、简要说明、项目目录、仓库、代码与文档入口 |
| 业务背景与目标 | 使用对象、场景、当前做法、主要困难、期望结果 |
| 本轮任务 | 当前问题、交付内容、完成标志、范围与排除项；与项目长期目标分别记录 |
| 当前状态 | 已有构想、原型、实现及实际使用情况，注明依据与不确定性 |
| 来源资料 | 客户资料、需求、设计、原型、历史决策、验证记录的位置、版本或时间及有效性线索 |
| 已有能力 | 业务模块、接口、工程设施、公共组件、内部工具和可复用资产的入口 |
| 技术基础 | 语言、运行时、框架、数据库、构建测试工具，关键第三方库、开源框架与外部服务的版本和用途线索 |
| 技术实践与经验 | 项目规则、开发测试发布方式、历史尝试、放弃原因、已知限制及经验出处 |
| 职责与约束 | 业务确认与验收职责、已有承诺、实际存在的时间资源限制、必须保留的行为 |
| 执行条件 | 运行命令、环境入口、可修改范围、验证条件与操作边界；在相关执行前补齐 |

技术信息优先从目录、依赖清单和项目规则获取，只索引影响当前工作或可能复用的关键项，不逐项抄录全部依赖；完整版本以清单和锁文件为准。区分项目已采用的技术、其他项目的可复用资产与经验、为当前需求新发现的技术候选；历史成功不自动证明当前适用，候选不写入既有技术栈。

项目阶段、目标、资料有效性和复用判断不能仅凭目录名、提交数量或依赖存在推定。初始化日期只能说明建档时间，不能默认是项目启动日期。凭据只记录配置位置，不收集或写入明文。

### 3. 索引优先与读取深度

采用满足当前判断所需的最浅读取深度，上一层足够时不进入下一层：

| 深度 | 动作 | 深入条件 |
| --- | --- | --- |
| 目录与文件名 | 识别区域、资料类别和可能的能力入口 | 尚不能分类或定位 |
| 清单与元信息 | 查看依赖、配置、标题、目录和版本 | 尚不能判断范围、关联或有效入口 |
| 关键片段 | 定向搜索和读取相关内容 | 当前重要判断仍缺依据，或来源存在冲突 |
| 专题调查与验证 | 深入代码、跨资料分析，必要时实际运行 | 下游工作确实依赖更强证据，另行明确问题、范围和验证条件 |

不默认启动项目、执行构建、跑测试或探测接口。只发现测试目录就登记测试资产入口；只发现认证目录就登记认证相关代码候选入口；依赖清单声明框架只证明声明存在。

索引记录名称与类别、位置、用途线索、判断依据，以及重要疑点。整体说明覆盖边界与读取深度，个别深入项单独注明；不为每个文件生成摘要，也不逐条重复“未运行”。索引服务后续按需读取，不直接生成已确认需求。

页面先登记路由、菜单、页面目录等可发现入口。只有具体需求或专题调查需要时，才沿“整体功能地图—单页功能—关键功能的数据、接口、状态与证据”深入，并从权限、异常、恢复和目标反查遗漏；该链路不是每次盘点的默认任务。前端可提供业务、代码与验证资产线索，但不自动证明需求或布局正确。

### 4. 候选、证据与补问

直接观察的事实注明出处；推断标明依据与不确定性；资料中的目标和历史约定先作为候选检查有效性。当前消息已明确的信息直接采用，不重复询问。

以下证据层级只描述已有依据，不要求盘点逐项完成三级核验：

- **存在**：有文件、代码、配置或文档记录；目录只证明入口存在。
- **可用**：有适用场景的实际运行或验证依据，注明范围和时间。
- **可承诺**：能力、授权、成本和稳定性足以进入特定交付范围，不能由盘点自行认定。

已有验证记录就引用，没有就停留在当前层级；不因未验证而给所有资产创建验证任务。只有影响后续判断的缺口才登记问题、影响和调查入口。静态存在不能推导可用，单次成功不能推导交付承诺。

使用 AskUserQuestion 收集无法自行查明且影响推进的背景、冲突与约定。每轮围绕一个主题提出少量相关问题，候选说明依据，允许 Other 自由填写及“暂不确定／稍后补充”；不为凑选项预设业务目标。不逐字段确认，也不通过整组确认把所有推断升级为事实。已有明确回答直接写入，仅对重要歧义继续追问。

先收集足以确定盘点位置和范围的信息，扫描后再补问。运行环境与操作条件在相关执行前补齐；缺失信息只阻塞依赖它的工作。新输入与档案不一致时，区分历史失效、描述错误、范围不同和需求变更，不静默覆盖，也不一律视为变更。

### 5. 完成与后续衔接

完成条件：项目背景与本轮任务足以支持下一步；相关来源和能力入口可查；覆盖边界及证据深度清楚；关键缺口、冲突和调查入口已有去处。无需证明所有能力可用或完成全部复用判断。

项目档案与来源索引是最小产物，复用已有等价位置即可；独立盘点报告、技术基线和验证记录仅按需产生。需求梳理、方案设计或执行中沿索引调查相关内容，新增证据回填原位置。现状说明现在有什么，需求说明决定做什么，方案说明怎么做，当前批次说明本次交付什么，四者不能混用。


## 持续使用时的项目上下文入口

项目持续使用本工作法时，在已有项目 CLAUDE.md 中增量增加简短导航，不覆盖既有规则、不改用户全局配置：

```markdown
## 项目工作入口
- 项目背景与本轮范围：.proj/artifacts/project-profile.md
- 来源与资产入口：.proj/sources/INDEX.md
- 业务术语：.proj/artifacts/ubiquitous-language.md
- 需求、设计或审计前读取相关业务术语与有效产物；从 .proj/README.md 定位当前依据和未决影响。
```

路径以实际存在的权威位置为准，不生成指向空文件的入口。短且所有任务都依赖的术语可用 CLAUDE.md 的显式 @path 导入；较大内容按任务读取，不能把普通路径链接当作全文自动加载。
