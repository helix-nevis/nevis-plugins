这套流程的主线是：**先知道“我们现在有什么”，再统一“我们在说什么”，然后决定“要做什么、怎么做”，最后通过执行证据持续校正。**

流程不是严格单向的。后续步骤发现前置结论不完整时，应回到对应步骤补充，但不能跳过确认直接修改既定结论。

本工作法的目的不是增加文档和人工审批，而是**把影响执行的不确定性逐步转化为已对齐、可验证的结论**。智能体依据明确边界推进常规工作，人只处理必须由人判断的事项，从而减少偏差、提高验收通过率、减少返工。

## 一、产物怎样才真正有效

一个内容只有满足以下条件之一，才值得进入长期产物：

- **执行依赖**：后续实施必须据此工作；
- **验收依赖**：判断是否完成必须引用它；
- **决策依赖**：缺少它会重复争论或改变重要取舍；
- **变更依赖**：后续修改需要知道影响和依据。

不满足这些条件的中间讨论、失败尝试、临时判断和重复日志，可以保留在过程记录或归档，不进入长期阅读入口。

### 1. 一套正文，分层阅读

人工阅读和智能体执行使用同一套事实源，不维护两套平行正文。文档按“概述—核心内容—规则与细节—追溯”自然组织：人通过概述快速判断方向，执行者按任务读取相关章节和契约。

### 2. 摘要、事实与证据分层

- **摘要**帮助快速理解，引用事实，不另立口径；
- **正文**保存当前有效结论；
- **证据**说明结论如何得到，保留环境、限制和来源。

证据和过程记录不能反向覆盖正文。事实发生变化时，应按对应权限更新正文，再保留必要证据索引。

### 3. 五个长期入口，两个过程目录

典型项目可以组织为：

```text
├── 起点与约束.md
├── 需求基线.md
├── 方案.md 或 方案/
├── 工作规划.md
├── 待决与决策.md
├── 执行/
└── 验证记录/
```

这只是信息结构，不要求小项目机械拆成同样多的文件。小项目可以合并为“起点与约束、需求基线、方案、工作规划”四份正文，待决与决策并入工作规划，执行和验证记录按需产生。

### 4. 四类贯穿信息的唯一归属

| 信息 | 权威位置 | 其他环节如何使用 |
| --- | --- | --- |
| 待决项与验证事项 | 统一清单，可附在待决与决策文件 | 发现时登记，阻塞处引用，关闭时回填正文 |
| 统一语言 | 需求基线 | 方案、契约、工作项和任务统一引用 |
| 追溯关系 | 需求、工作规划、交付记录分段持有 | 串成“需求—方案—工作项—证据”链路 |
| 重大决策 | 决策记录，只追加 | 正文引用结论，记录保留背景和权衡 |

不要在每一步分别建立待决台账、验证台账和完整追溯矩阵，形成多个互相竞争的事实源。

## 二、讨论与落实的基本节奏：总—分—总—分

每个环节都采用同一节奏：**先整体对齐，再分点对齐；先形成整体结论，再分点落实。** 对齐首先是确认双方讨论的是同一个问题、同一层目标和同一组边界，不是一开始就对所有答案达成一致。

1. **先整体对齐**：说明为什么讨论、要解决什么、处于哪个层次、什么已确定、什么不在本轮范围。可以提出结构草案供校正，但不能把所有细节当成既定事实。
2. **再分点对齐**：逐项处理关键分歧，区分事实、假设、建议和待决定内容，说明选项、依据、代价和影响。依赖未定的子问题延后，不强行拍板。
3. **回到整体形成结论**：重新检查目标、范围、核心规则和各部分关系，避免把零散回答直接拼成最终方案。整体确认前，单独列出新增关键假设、默认行为和用户新增负担；整体确认不等于确认未显式说明的关键默认值。
4. **最后分点落实**：分别更新术语、需求、方案、决策、验证事项和工作项，保留结论与修改位置的对应关系。

每轮讨论都应回答：**整体是什么，本轮对齐哪些点，合并后的结论是什么，结论分别落到哪里。** 整体未对齐时继续澄清，不用细节数量制造确定性；整体结论未确认时，不进入全面实施。

## 三、默认推进，异常升级

事实查证、资料整理、常规设计修正、自动检查、测试执行、状态更新和证据整理由智能体默认推进，不要求人工逐项审核。

只有以下事项需要升级：

1. 目标、核心范围、需求基线和验收承诺的变化；
2. 重大方案取舍、公共契约和关键技术路线；
3. 费用、账号、真实数据、外部写入、迁移和部署等授权；
4. 无法自行消解的矛盾及高影响未决事项；
5. 批次验收结论，以及是否进入下一批。

**不逐项人工审核，不等于不逐项分析。**智能体先在内部细致扫描事实、识别假设、推演场景、比较替代方案，并检查用户成本和返工影响，再减少对外提问。默认推进有依据、低影响且可逆的常规工作，不是未经审视的关键假设；智能体负责把细节想透，人只处理真正需要人决定的取舍。

“默认推进”不等于无限授权，“人工判断”也不等于逐条审批所有常规内容。若人工接触点远超上述五类，通常说明目标、边界或产物仍未写清，而不是审核得不够。

## 第零步：现状盘点与起点确认

对于已有原型、代码、文档或运行系统的项目，先盘点影响当前判断的现状，再梳理目标需求。避免把“现状如此”误当成“需求如此”，也避免把“曾经做过”误当成“应该保留”。

本步回答“现在有什么、凭什么推进”，后续需求和技术设计还会继续按需加深盘点，不在起点追求一次性全量盘清。

| 盘点对象 | 需要回答的问题 |
| --- | --- |
| 业务与资料 | 哪些规则、流程、样例和外部约束仍然有效？ |
| 产品与技术资产 | 哪些原型、代码、数据、接口和组件可以复用，运行状态如何？ |
| 团队能力 | 谁负责需求、设计、开发、测试和验收，关键技能是否有缺口？ |
| 工程设施 | 仓库、环境、数据库、存储、部署、监控和持续集成是否具备？ |
| 外部资源 | 平台、模型、账号、授权、额度和预算条件是什么？ |

盘点结论区分三个层级：

- **存在**：有文件、代码、账号或文档记录；
- **可用**：已经实际运行或验证过；
- **可承诺**：能力、授权、成本和稳定性足以进入交付范围。

“盘上存在代码”不能推导出“能力已经可用”，“接口调用成功一次”也不能推导出“可以纳入交付承诺”。

本步形成**现状基线**：说明现在有什么。需求基线说明决定做什么，方案说明决定怎么做，当前批次说明本次具体交付什么，四者不能混用。

### 执行方法

**1. 覆盖地图与分层扫描：广度完整，深度分级。** 建立信息来源与业务区域覆盖地图，记录来源位置、可证明的事实、证据状态和未核验区域。全面扫描不是逐行通读全部资料；先读目录、摘要、决策、入口、权限、核心对象、接口和测试名称等高信号入口，再沿高价值场景跨资料追溯，低信号内容识别后跳过。从入口、权限异常和文档目标反向检查遗漏，保留未深入范围，不把局部抽样说成完整审计。

**2. 事实清单法：先扫描，再抽样核验。** 建立与当前判断有关的资产、人员、环境和资源索引；只对影响复用和选型的关键项做运行、构建、探活或访谈验证，不一开始全量测试。

**3. 证据标记法：分开事实、推断和待验证。** 事实能定位到文件、运行结果、配置或责任人；推断写明依据和反证条件；无法静态确认的内容登记为验证项。报告提供证据，不代替决策。

**4. 复用边界法：区分继承、改造和重建。** 明确复用的是代码片段、结构、数据模型还是运行能力，同时列出目标差异。能读取代码不等于能继承业务模型。

**5. 能力访谈法：区分做过、能独立交付、能负责验收。** 同时确认实际经验、投入程度、评审能力和岗位备份；环境区分本机可运行、团队可复现和生产可使用。

**6. 风险抽样法：优先验证会改变路线的未知数。** 只读核验与产生费用、写入或外部影响的核验分别授权。

**退出检查：** 影响当前判断的现状有位置和证据状态，主要复用边界与硬约束已登记，未验证能力没有被写成事实。

**最小有效产物：**

1. 起点与约束清单；
2. 盘点异常及统一待决、验证项；
3. 原始盘点与验证记录，按需归档并保留索引。

## 第一步：需求梳理与统一语言

基于现状、已有资料和业务沟通提炼需求，同时建立轻量统一语言，避免后续讨论在词汇歧义中反复消耗。

### 先建立轻量统一语言

本步不追求一次性完成领域模型，只收敛核心业务概念：

| 内容 | 作用 |
| --- | --- |
| 规范名称 | 后续统一使用哪个词 |
| 简短定义 | 这个概念是什么 |
| 非等价词 | 哪些近义词不能混用 |
| 边界与反例 | 什么不属于这个概念 |
| 当前状态 | 已确认、暂定或存在冲突 |

定义回答“它是什么”，不描述系统如何实现。术语一经澄清立即记录，并用具体场景检验边界。例如“完成”指生成成功、用户采纳还是业务定稿，“保存”指暂存、文件落盘还是正式入库。

资料或代码能够回答的问题先自行查证。口头描述与代码行为不一致时，区分“当前实现如此”和“目标业务应当如此”，不能用其中一方自动覆盖另一方。

### 再梳理和确认需求

先区分业务目标、用户任务、业务规则、当前做法、方案建议、技术实现、隐含假设和待决事项，保留出处。文档写了、代码存在或行业常见都不能单独证明需求成立。按“事实地图—核心角色与高价值主线—场景合并证据—候选需求—内部推演—整体基线”推进，不逐行把每句话判成需求，也不读完后未经追溯直接下结论。

登录、身份识别、组织归属、权限、角色和进入条件属于需求，不是可默认套用的技术设施。凡要求用户提供内部标识、额外信息、专业知识或前置准备，必须确认来源、必要性及系统能否自动取得。邮箱、手机号、企业 ID、邀请码不得仅因常见或易实现而成为默认方案。

每项需求从三个维度判断：

- **重要程度**：核心、非核心或明确不做；
- **明确程度**：已经想清楚或仍有歧义；
- **确认方式**：讨论可以确定，或必须依赖调研、测试和外部条件。

目标、规则和优先级不清时向业务方提问；外部能力不清时登记验证，不用讨论代替验证。暂时不能确认但不影响整体设计的，可带假设推进；影响核心范围的，暂停相关设计。

需求使用稳定编号，形成可确认、可变更的基线。基线明确范围、排除项、待确认事项和变更规则；确认基线不等于批准开发。

### 执行方法

**1. 决策树访谈：先主干，再按依赖反问。** 可借鉴 `/grill-with-docs`：先给出问题全貌和决策主干请对方校正，再展开前置条件已明确的问题。对核心候选需求围绕目标、场景、责任、边界、异常和替代方案多轮递进反问，每轮依据上轮答案推演，不一次抛出完整问卷。每题给出建议、选项和代价，事实先自行查证。分点完成后先汇总整体理解，再写入基线。

**2. 场景推演：一次验证一个真实问题。** 从高频主链路沿“触发—输入—业务对象—责任动作—结果—异常恢复”走查。没有业务依据的低频分支只登记，不展开。

**3. 边界追问：用正例、反例和极端情况定规则。** 优先澄清从何时开始不算、失败后算什么、重复操作怎么办、谁有权推进和是否允许后补。

**4. 责任分离：分清决策、执行和系统记录。** 对关键动作确认谁提出、谁决定、谁执行、谁留痕，不让普通消息或返回结果替代明确的业务动作。

**5. 反向排除：明确不做什么。** 区分当前阶段不做与永久不需要，避免后续专项被误删或提前塞入本期。

**6. 编号追溯与冻结检查。** 编号发布后不因排序重排；冻结前集中处理核心口径、范围、指标和验收影响，普通页面细节不阻塞整体基线。

**退出检查：** 高频主链路能走通，核心概念无同词异义，关键责任与状态推进清楚，核心范围和排除项已确认，遗留事项均有处理方式。

**最小有效产物：** 一份需求基线，按以下顺序组织；小项目可合并章节，不单建“人工版”或“智能体版”。

```markdown
# 需求基线
## 一、概述
## 二、核心需求
## 三、业务规则与边界
## 四、统一语言
## 五、待讨论事项（引用统一清单）
## 六、需求追溯
```

## 第二步：方案设计

基于已确认需求和统一语言，设计业务流程、领域模型、产品交互、系统架构和实现路径。不同方向可并行，但每类信息只有一个权威来源。

统一语言在本步发展为领域模型：**术语回答“在说什么”，概念关系回答“如何关联”，领域模型回答“对象如何构成业务”，接口与数据模型回答“系统如何交换和保存事实”。**

领域模型至少明确核心实体及身份、关系与边界、生命周期与状态转换、创建和修改责任、必须长期保存的事实，以及不同上下文如何引用。

方案重点回答：用户如何完成任务，对象和状态如何变化，模块如何协作，技术栈及关键约束是什么，哪些能力必须验证后才能承诺。

方案内部边设计边交叉检查；独立方案审计在候选方案形成后进行，两者不能互相替代。

### 执行方法

**1. 业务事实优先：先对象和状态，再页面和模块。** 从业务动作反推必须保存的对象、关系、输入快照、操作人和结果；页面是事实的视图，不为每个页面复制状态。

**2. 交互策略与布局决策：先任务和形态，再组件。** 检查已有页面、原型、设计系统和典型任务，区分可继承依据、存疑惯例与明确反模式；现状是证据，不是设计正确性的证明。依据用户任务、信息层级、操作频率、比较和跨阶段切换确定工作台、列表—详情、编辑器或向导等产品形态。**流程描述业务推进关系，不直接决定页面结构，不得把业务流程、工作项或后台处理阶段机械映射为步骤卡片。**

现有前端与任务目标冲突、依据缺失或相互矛盾、存在多种高影响形态，或需要改变整体导航、核心操作习惯和视觉方向时，先给出带依据的推荐、备选与代价，请用户确认；不泛泛询问“设计原则是什么”，局部组件和常规样式仍默认推进。

**3. 状态机与故障矩阵：显式设计异常。** 对核心对象列出推进、失败、超时、取消、重试和迟到结果；对外部依赖列出不可用、重复响应、部分成功、限额和恢复方式。

**4. 风险驱动设计：先做深不可逆和难恢复的问题。** 身份权限、核心标识、事务并发、文件生命周期、外部副作用和恢复路径优先；普通展示和非关键字段后补。

**5. 适配边界与降级：隔离外部不确定性。** 外部服务通过稳定接口接入，定义正常、降级和失败关闭路径。未经验证的能力不进入核心承诺，不用假状态冒充真实成功。

**6. 多线交叉走查：用同一业务场景贯通流程、领域、交互和技术。** 冲突先登记位置和影响，再裁决并同步修改，不直接采用“最新修改版本”。

**7. 现成优先与最小实现：说明选型约束和退出成本。** 自研集中于真正有业务差异的部分，只建设当前范围和必要衔接。

**8. 核心契约先行，执行细节后补。** 方案阶段明确核心业务语义、权限、状态、幂等、事务和恢复；普通字段、完整请求响应、索引和迁移细节可在对应工作项开工前补齐。

**退出检查：** 核心对象及状态有唯一口径，关键异常与恢复可实现，权限与外部副作用有边界，技术选型与待验证项已分开，典型场景能贯通四种设计视图；涉及界面时已明确产品形态、信息层级和主操作路径，未以流程分段代替布局设计。

**最小有效产物：**

```text
方案/
├── 产品交互方案.md
├── 领域模型.md
├── 技术方案.md
├── 开发规范.md
├── 契约/
│   ├── 接口设计.md
│   ├── 数据库设计.md
│   └── 外部服务契约.md
├── 决策记录.md（或引用统一决策入口）
└── 验证记录/
```

小项目可以合并。机器可读契约可由 OpenAPI、Schema 和迁移文件承载，Markdown 解释业务语义和约束，避免重复所有字段定义。工作项、接口和数据库设计不得各自复制一套业务规则。

《产品交互方案》用一节记录设计依据、核心任务、选定形态及原因、信息层级、主操作路径、关键取舍和明确避免的模式，不另建长文档。设计系统或项目已有规范仍是其权威来源，不在工作项和审计记录中重复维护。

## 第三步：方案审计

对候选方案进行独立检查，而不是只检查文档是否齐全。审计覆盖：方案内部是否自洽，需求是否完整覆盖，方案是否具备规划条件。

审计采用**默认通过、异常升级**：常规一致性和覆盖检查由智能体完成，只把矛盾、缺证据、重大取舍和不可规划事项提交责任人，不要求人工逐项打勾。

问题按性质分流：

- **设计类**：进入统一待决项，由责任人决定；
- **证据类**：进入验证事项，通过资料、原型、测试或真实环境解决；
- **规划类**：在工作拆解时补充，不影响整体方案的可延后。

按影响区分阻断、局部回填和后续登记。**审计坚持审查与决策分离**：审查者可以判断不一致、缺证据或不可开工，但不能自行改变业务目标、核心范围、重大技术路线和验收承诺。

可能推翻核心方案的未知，不应等完整审计结束才处理，应尽早启动低成本**短探针**。

### 执行方法

**1. 双向追溯：需求向实现查，方案向来源查。** 正向检查需求是否有流程、交互、技术和验收入口；反向检查关键规则是否追溯到需求或明确决策。同时检查用户被要求提供的信息是否可获得，是否把内部实现概念转嫁给用户，系统能否代替用户判断，是否有更低负担且不改变业务结果的方案。

**2. 对抗性案例审查：专找实际会错的情况。** 围绕重复提交、并发推进、迟到结果、部分失败、越权、恢复和限额构造反例，检查业务事实是否会被覆盖、伪造或错误推进。

**3. 布局反证：检查页面是否服务真实任务。** 检查是否把业务流程直接画成步骤卡片、把后台阶段误当用户步骤、用重复分区割裂信息层级，或迫使用户频繁滚动、跳转和返回。去掉卡片容器后布局逻辑仍应成立。现有页面与设计原则冲突时，不因现状存在而判为合理；涉及整体形态或核心操作习惯的变化，提交带依据的候选由责任人确认。

**4. 证据卡：把验证目标写成可执行记录。** 明确对象、环境、输入、步骤、完成证据、限制和结论；一个成功案例不能代替整组能力，部分通过必须列出未通过范围。

**5. 短探针：先验证最可能推翻方案的假设。** 限定问题、成本、输入、时长和停止条件，只回答一个关键未知；探针结果进入证据层，重要结论再回填正文。

**6. 分级闭环：区分阻断、回填和登记。** 阻断问题关闭前不得实施相关工作；局部问题明确回填；纯优化和未来事项登记。完成条件是问题已解决或有明确安排，不是会议已召开。

**退出检查：** 核心需求双向追溯无断点，阻断问题已关闭，关键假设已有证据或验证安排，裁定已回写，剩余事项不妨碍规划。

**最小有效产物：**

1. 一个短审计入口和整体结论；
2. 实质异常及影响，不复制所有正常检查项；
3. 统一待决项、验证事项及证据索引；
4. 回填后的需求、方案和追溯关系。

## 第四步：工作规划

把已对齐方案组织成可以按依赖实施、按证据验收的工作，并明确哪些现在可以开始，哪些仍需等待。

**工作项不是越细越好，粒度停在“主要依赖明确、能够独立验收”的层级。** 工作项是规划层的可独立交付能力；开工前的执行任务才是实施层的具体工作。一个工作项可以包含多个执行任务，不必提前细化未来全部任务。

每个工作项至少说明：编号与名称、对应需求、交付目标、范围边界、方案依据、前置依赖、验收标准、未决约束和状态。工作项只引用权威正文，不复制需求、方案、接口或数据库内容。

依赖分为五类：**方案依赖、能力依赖、证据依赖、资源依赖、验收依赖**。分层用于识别公共地基，垂直切片用于尽早交付真实业务价值，两者结合而非互相替代。

拆解也是一次再审计。新发现的设计分歧、外部未知、资源不足和未来优化分别回到统一待决、验证、开工条件和后续候选，不为了让清单完整而自行补定结论。

**工作规划与开工授权必须分开。** 清单完成只说明可以怎样组织工作，不代表允许开工、付费调用、迁移、部署或使用真实账号。

### 执行方法

**1. 依赖分层：识别公共地基。** 前后置关系指向具体交付物，不能只用阶段名称表达依赖。

**2. 工作项画布：同页写清需求、边界、依据、依赖、验收和约束。** 无法填写验收或关键依赖的工作项，通常不具备继续细化条件。

**3. 两级拆解：规划级与执行级分开。** 只有当前批次且依赖成熟的工作项才拆成执行任务，避免全量过早细化。

**4. 垂直切片：尽早贯通真实主链路。** 共同地基稳定后，选择端到端且能证明业务价值的切片；切片包含真实状态、持久化和异常恢复，不用演示路径代替。

**5. 缺口登记：问题回到对应权威位置。** 不在工作项中隐藏不确定性，也不另建重复问题台账。

**6. 授权门：分别确认范围、资源、环境、外部权限和验收责任。** 排期与实施均需明确授权，未授权的高影响操作不得提前执行。

**退出检查：** 每项工作有边界和验收，关键依赖无悬空，当前批次及衔接可以解释，新发现缺口已分流，规划和授权没有混同。

**最小有效产物：**

1. 规划级工作项清单及依赖；
2. 当前批次说明：目标、包含与不包含项、交接顺序、端到端验收和下一批入口；
3. 开工条件与授权事项；
4. 新发现问题的统一清单引用。

最重要的不是大任务表，而是说清：**现在做哪一批、为什么能做、如何衔接、怎样算完成。**

## 第五步：任务派发与执行反馈

把当前批次转化为执行者可以独立完成的任务，并用交付证据、独立审查和偏差处理证明任务真正完成。

**验收标准必须先于实施确定。** 开工说明使执行者不依赖原会话记忆也能工作，至少包含：任务身份与目标、所属工作项、执行边界、必读依据及章节、实施约束、环境与权限、验收标准和交付格式。

开工说明同时写明升级条件：需要改变需求或范围、方案存在实质冲突、必须修改公共契约、真实外部行为推翻假设、需要新增高影响权限，或验收标准本身不成立时，停止相关扩展并提交判断。

执行过程只保留有助于协作、排查和交接的信息，不写工具调用流水账。简单任务可以只有变更、测试和审查记录；复杂任务再增加交接说明。

交付后独立审查任务边界、需求与规范符合性、验收覆盖、关键实现、外部副作用、占位实现和文档一致性。测试环境可能掩盖真实行为时，应增加接近真实环境的验证。

执行反馈分四类处理：

- **实现偏离方案**：修实现并重新验证；
- **方案存在缺口**：回填方案并评估影响；
- **外部事实推翻假设**：保存证据，调整设计或默认行为并回归；
- **需求或范围变化**：说明原因、成本和验收影响，经确认后变更基线。

任务只有在交付、审查和必要回归完成后才能关闭。未完成事项、临时限制和遗留风险必须进入统一清单，并说明对后续工作的影响。

### 执行方法

**1. 开工单：把验收、边界和权限随任务下发。** 复杂任务分批交接，后续批次等待关键前置审查通过。

**2. 小步可证交付：每个交付都有对应证据。** 提供变更位置、自动化测试、运行结果和必要说明，不用大段描述代替证据，不留下无明确验收的占位实现。

**3. 独立审查：同时看测试和关键实现。** 重点检查权限、事务、并发、恢复和外部副作用；“有条件通过”必须写明条件、可用范围、限制和后续处理。

**4. 根因处理：失败先判断契约还是实现有误。** 不通过删除用例、放宽断言、吞掉异常或修改业务口径制造通过。

**5. 受控实测：外部验证单独设边界。** 涉及费用、账号、真实数据、外部写入或部署时，先明确授权、预算、输入、脱敏和停止条件；敏感配置和密钥不进入文档或代码库。

**6. 偏差分诊与回归：修正后验证影响面。** 改变默认行为、公共契约或核心模型后，重跑受影响范围，并更新交付记录和遗留项。

**退出检查：** 验收逐条有证据，独立审查完成，环境限制已说明，偏差正确归口，遗留项有后续责任，敏感信息未进入记录。

**最小有效产物：**

1. 任务开工说明；
2. 交付、测试证据与独立审查记录；
3. 必要的需求、方案、契约和验证更新；
4. 统一遗留事项及工作项状态；
5. 当前批次的轻量业务验收结论。

### 批次业务验收

技术任务关闭不等于业务目标达成。当前批次结束时，由目标角色或责任人复核核心场景：最初的问题是否解决，哪些路径仍依赖降级或人工处理，是否引入新的使用成本，是否达到批次完成标准，下一批应继续、调整、暂停还是补验证。

验收记录只需保留已走通场景、未通过或受限场景、与原始目标的差距、继续使用条件和后续建议。可以并入工作规划的当前批次部分，不必为简单批次新建长报告。

## 四、产物的生命周期与收尾规则

| 产物 | 创建时机 | 更新条件 | 收尾方式 |
| --- | --- | --- | --- |
| 起点与约束 | 第零步，后续按需加深 | 发现新的现状事实 | 保留当前有效结论 |
| 需求基线 | 第一步 | 仅获批的需求变更 | 保留当前基线与必要变更记录 |
| 方案与契约 | 第二步 | 审计回填、执行偏差、外部假设被推翻 | 保留当前有效方案 |
| 待决与验证清单 | 全程 | 发现即登记，解决即关闭 | 结论回填正文，开放项保留，历史可归档 |
| 决策记录 | 按需 | 只追加 | 长期保留背景与权衡 |
| 工作规划 | 第四步 | 状态和批次变化 | 当前批次保留，历史批次归档 |
| 任务与交付记录 | 执行期 | 任务推进和关闭 | 保留证据索引，过程可归档 |
| 过程日志 | 按需 | 排查与交接需要 | 默认归档，不进入长期正文 |

关闭待决或验证事项时，必须把结论写回需求、方案、契约或工作项，清单只保留指针。否则清单会成为第二套事实源。

追溯不必集中维护一张大矩阵：需求基线持有“需求—方案”，工作规划持有“工作项—需求与方案”，交付记录持有“任务—工作项与证据”。三段串联即可双向检查。

## 五、贯穿全程的八条原则

### 一、先对齐，再结论；先整体，再局部

讨论从整体理解开始，经分点澄清后回到整体结论，最后分点落实。整体未对齐不展开所有细节，局部结论未组合校验不视为完整方案。

### 二、单一事实来源

同一类信息只有一个权威来源，其他位置引用而不复述。术语进入统一语言，业务规则进入需求或方案，实体关系进入领域模型，重大权衡进入决策记录，待验证内容进入统一验证清单。重要结论不能只留在会话中。

### 三、证据分级

文档与静态检查、可运行原型、专项技术核验和真实场景验收的证明力不同。不能把设计合理当成已经验证，也不能把部分通过写成全部通过。

### 四、未核验，不承诺

依赖外部平台、供应商、性能或真实环境的能力，在取得证据前只能作为假设或候选方案，不能作为确定交付范围。

### 五、审查与决策分离

分析和审计负责说明问题、选项、代价和影响，最终结论由对应责任人作出。只有难以逆转、缺少背景容易令人意外且存在真实权衡的决定，才形成独立重大决策记录；普通结论进入正文。

### 六、统一语言持续对齐

审计、规划和执行中发现概念歧义或模型无法表达真实业务时，应回到统一语言或领域模型修正，再同步受影响内容。新术语不能由单个任务临时创造后自然扩散。

### 七、粒度随依赖收敛

依赖未定时保持较粗粒度，依赖明确后再细化。规划级用于范围和依赖，执行级用于当前实施，不以拆得最小为目标。

### 八、基线与授权分开管理

现状基线、需求基线、方案确认、工作规划和开工授权是不同决定。前一环节完成不自动意味着后一环节获批；已确认内容的修改必须留下原因、影响和批准记录。

## 结语

这套流程的关键不在于文档数量，而在于五个闭环：**现状能够支撑需求判断，需求能够追溯到方案，方案能够追溯到工作项，执行结果能够反过来校验方案，批次验收能够回答最初的问题是否真正解决。**

统一语言贯穿其中，默认推进与异常升级控制协作成本，最小有效产物保证信息值得长期保存。只要这些机制存在，具体使用什么文档、工具和项目管理系统都可以调整。
