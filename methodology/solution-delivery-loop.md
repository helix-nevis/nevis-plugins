# 方案收敛与交付闭环工作法

> 文档版本：v1.5 工作稿；更新日期：2026-11-18。
> 本文说明工具无关的方法、概念与协作原则。具体项目的需求、方案和授权由相应责任人确定。

这套工作法把影响执行的不确定性逐步转化为已对齐、可验证的结论：先建立对项目与现状的共同理解，再澄清业务需要、形成方案、独立审计和规划，最后通过交付证据检验最初的问题是否解决。

目的不是增加文档和审批，而是减少未经审视的假设、断裂的交接和无效验收。常规工作依照明确依据推进，人集中处理目标变化、重大取舍、矛盾、授权和业务验收。可以由人工团队、智能体或二者协作采用，不依赖某种软件平台。

## 一、概念与层次

| 概念 | 含义与边界 |
| --- | --- |
| 诉求 | 相关方表达的愿望、困难、期望或提出的办法；需要理解其背后的意图，不直接等于已确定需求 |
| 需求 | 从诉求、业务规则及有效约束形成的要求，明确条件、角色、行为或结果、质量和边界 |
| 业务活动 | 有目的、输入、责任和结果的业务单元 |
| 业务流程 | 业务活动及其衔接，描述业务如何完成，不受拟建工具和系统限定 |
| 操作流程 | 业务活动落到界面或其他人机交互方式后，用户如何操作、系统如何反馈并完成任务 |
| 实现路径 | 系统内部的信息处理与协作过程，包括输入、处理、状态、保存、输出与故障恢复 |
| 技术方案 | 支撑需求的结构与技术设计，包含架构、职责、选型、部署、契约及实现路径；范围大于一条处理流程 |
| 系统与子系统 | 系统是有目标和边界的整体；子系统承担其中相对完整的职责，不必独立部署 |
| 功能 | 系统向角色或其他系统提供的可识别行为或能力；功能名称不等于完整需求 |
| 模块 | 为组织技术职责与实现而划分的单元，不与页面、功能或交付批次强制一一对应 |
| 工作项与任务 | 工作项组织有边界、依赖和验收的交付结果；任务是实施时进一步拆出的具体工作 |

这些概念不是一棵固定分解树。一项需求可以跨多个模块，一个模块也可支持多项需求；一个工作项可以跨功能和子系统。质量要求和约束也是需求，不一定对应独立功能。

业务流程必须说明为什么需要某个活动、需要哪些信息、核心关注什么、谁承担责任及产生什么结果。箭头可以概括顺序，不能代替业务说明。操作流程不等于实现路径；后台有多个处理阶段，不代表用户必须逐步操作。

## 二、协作与收敛原则

### 1. 总—分—总—分

1. **整体理解**：对齐问题、目标、当前层次、已知依据与本轮边界，允许提出草案，不把假设写成事实。
2. **分点调查与澄清**：优先处理前置条件明确、会影响后续工作的少量问题。能查证的先查，需责任人取舍的再询问。
3. **重新组合**：检查局部结论组合后是否自洽、遗漏或引入新冲突，再进行必要确认。整体认可不自动批准未显式说明的关键默认值。
4. **分别落实**：更新对应的诉求、需求、术语、方案、事项、决策和工作项，使修改位置与结论对应。

局部修正后重新检查整体，不能因为当前暴露的问题解决，就跳过其他前置缺口继续实施。每轮应能说明整体是什么、本轮解决哪些问题、组合后的结论和分别更新的位置。

### 2. 默认推进，异常升级

资料调查、事实核对、候选分析、常规设计、已授权验证和记录更新由执行者主动完成。需要升级的主要是：

- 目标、核心范围、已确认需求或验收承诺的变化；
- 高影响产品形态、关键技术路线与公共契约取舍；
- 超出既有授权的费用、账号、真实数据、外部写入、迁移、部署或生产影响；
- 无法自行消解的矛盾和高影响未决；
- 批次业务验收与后续推进决定。

不逐项人工审核，不等于不逐项分析。执行者先细致检查事实、假设、反例、替代办法和用户负担，只将需要责任人决定的内容提交。提问说明背景、推荐、选项、代价和影响，不为避免提问而自行决定关键问题，也不把全部查证责任转交用户。

### 3. 证据、判断与责任分开

区分事实、推断、建议和待决。设计合理不等于已经验证，部分通过不等于全部通过。审查者可以判断不一致、缺证据和不具备开工条件，但不能擅改目标、核心范围或验收承诺。

工作可以按性质分工：调查、候选比较和独立审查由适合的参与者承担，关键沟通与整体整合有明确责任人。交接提供问题、范围、依据、结论、证据状态、未覆盖范围和待决影响，接收者核对后采信。独立审查应尽量由未参与原设计的视角进行；零散摘要不能代替对整体关系的重新校验。

## 三、最小有效产物与信息组织

### 1. 什么值得长期保存

仅当后续执行、验收、决策或变更需要依赖时，内容才进入长期产物。中间推演、失败尝试和临时判断可保留在过程材料中，不持续占据正式阅读入口。

人工与智能体共用同一套事实源。摘要帮助理解，正文保存有效结论，证据说明结论如何得到；摘要和过程记录不能静默覆盖正文。正式产物可以包含明确标记的候选和未决，保存位置本身不表示已经确认。

### 2. 按职责组织信息

| 信息 | 职责 |
| --- | --- |
| 项目档案 | 项目身份、业务背景、目标、责任、约束与相关入口 |
| 来源与资产索引 | 资料和能力在哪里、用途线索、观察依据、覆盖范围及重要疑点 |
| 客户诉求清单 | 用户原意、来源、澄清与处置结果 |
| 统一语言 | 项目业务概念、定义、边界及当前状态，独立维护供其他产物引用 |
| 需求文档 | 场景、业务流程、功能、规则、质量、约束、范围、验收和迭代范围 |
| 方案与契约 | 系统怎样支撑需求，各设计视图与协作边界 |
| 工作规划与交付记录 | 交付结果、依赖、批次、验收条件与实际证据 |
| 统一事项与重大决策 | 未决问题及其闭环，重要选择的背景和理由 |

来源原件、未分类输入、草稿及正式产物应有可辨认的归属。未分类不等于未确认：已识别的需求、冲突或验证问题应进入相应产物并标明状态。既有资料通常保持原位置，通过索引关联；不为整理复制另一套有效正文。

这些是信息职责，不是固定文件数量或目录要求。复用项目已有权威位置，小项目可以合并承载，但不同类型内容仍应容易区分。

### 3. 引用与闭环

下游维护上游依据的引用：诉求引用原始消息、材料或界面；需求引用诉求或明确约束；方案引用需求；工作项引用需求和方案；交付引用工作项与证据。一项内容可以有多个依据，通过引用反查承接与覆盖，无需手工维护两套映射。

待澄清、待决策、冲突与待验证事项使用统一入口，说明问题、来源、影响、处理安排、状态及结论回填位置。验证证据与问题记录分别维护；关闭时将结论回填对应正文，事项保留证据和回填引用。

重大决策只记录难以逆转、缺少背景容易令人意外且确有权衡的选择，保留当时背景、选项、代价和影响，不改写历史。普通结论写入对应正文。

## 四、六个环节

各环节可按本轮任务单独开展，也可衔接推进。发现前置缺口时回到相应环节；进入某一环节不代表必须执行全部流程。

### 第零步：项目初始化与现状盘点

**目标**：明确项目归属、资料范围和现有条件，为下一步建立可靠入口。

先区分本轮讨论和产物的归属、资料来源位置、实施位置及实际工作位置。它们可以相同，也可以分离；实施位置尚未确定不妨碍业务讨论。盘点前确定相关入口、用途与排除范围，后续增量补充，不要求开始前穷尽全部来源。

按需收集项目背景、使用对象、目标、本轮任务、实际状态、职责、承诺、资源和执行约束，以及已有业务能力、技术基础、第三方能力、实践和可复用资产。区分已采用技术、历史经验和当前新候选，不能仅凭目录名、资料记录或惯例推定有效性。

**方法**：

- **索引优先**：先看目录、名称和元信息，足以定位和分类就停止；不默认读完资料或运行系统。
- **按问题深入**：只有当前重要判断缺依据、入口不明或来源冲突时，定向读片段、开展专题调查或验证。
- **证据标记**：存在、可用、可承诺分别说明已有记录、适用场景验证和可承担的交付责任；不是盘点必须逐项达到的三级目标。
- **先查后问**：已有回答不重复问，缺失信息只阻塞依赖它的工作。历史失效、描述错误、范围差异和真实变更分别处理。

现有界面、代码和样例是调查入口，不证明目标需求或交互合理。只发现某模块或测试资料时，不宣称功能可用；相关设计需要时再明确复用边界。盘点形成项目档案、来源与资产索引及关键缺口，不强制独立长报告。

**完成条件**：背景与本轮任务足以支持下一步，相关入口可查，覆盖边界和依据深度明确，关键缺口有处理入口。

### 第一步：需求梳理与统一语言

**目标**：理解客户意图，形成有来源、可解释、可验收的业务要求。

来源包括当前输入、文档、现有界面和历史对话；实现、接口和验证材料辅助解释现状。先区分目标、诉求、规则、当前做法、方案建议及隐含假设，再跨来源组合，而不是直接将现有按钮、技术选项或行业惯例当作需求。

**调查循环**：整体理解目标、角色、场景与业务流，建立调查问题，带着问题查资料；无法查明或需业务取舍时询问责任人，答案产生新问题就继续调查，最后回到整体校验。问题可分澄清、启发和确认三类；启发性建议是候选，不自动成为新增需求。不重复抄录全部问答，保留来源和有效结论。

**分析方法**：

- 沿业务活动检查目的、触发、角色、信息、核心判断、结果、交接与异常；用正例、反例、重复、失败、越权和恢复检验边界。
- 对核心需求多轮递进澄清，每轮依据上轮答案推演，不一次发完整问卷，也不只重复请求确认。
- 先理解用户怎样发起、控制和完成任务，再讨论命令、界面和实现；高影响入口、操作习惯、身份权限和对象关系用具体场景有效对齐。
- 审查用户新增负担和信息可获得性。登录、组织归属及访问条件是需求，不因常见或易实现默认采用；能自动取得的信息不轻易转嫁给用户。
- 合并同意图诉求并保留多源，按真实任务拆分复合诉求；保留暂缓、否定、替代或不采纳的原因。

功能需求说明：在什么场景下，哪个角色需要系统提供什么行为，遵守什么规则，得到什么可观察结果。名称、描述、依据和验收是基础，复杂规则按需展开。重要程度、确认状态与迭代安排分别表达，当前不做与永久排除分开。

本步维护三个产物：客户诉求清单、独立统一语言与需求文档。统一语言及时记录概念、非等价词和反例，不等讨论结束再补；需求文档的确认基线表示已确认的要求，不另造一套正文。业务功能按能力分组，不提前确定代码模块或开发任务。

**完成条件**：核心业务链路可推演，概念、责任、规则与边界清楚，诉求有承接或处置，需求有依据及可验证结果。影响当前基线的问题已解决、排除或隔离，非阻断问题有安排，不要求全部清零。确认需求不等于批准开发。

### 第二步：方案设计

**目标**：说明系统怎样支撑已明确的业务要求，并使方案具备审计与规划条件。

引用需求、统一语言、业务流程和现状资产，明确本轮范围。提取驱动设计的硬约束、关键质量、外部边界、规模和使用条件、真实取舍及关键未知。设计驱动因素引用需求，不再复制一份需求。

围绕同一核心场景，按依赖协同细化四个视图：

| 视图 | 关键内容 |
| --- | --- |
| 领域与业务状态 | 对象身份、关系、责任、规则、生命周期、状态变化及长期事实 |
| 产品与操作流程 | 产品形态、信息层级、入口、用户动作、自动行为、反馈、结果与中断恢复 |
| 系统架构与实现路径 | 系统边界、子系统和模块职责、通信、处理路径、状态归属与部署 |
| 数据与接口契约 | 事实如何保存，跨边界读取和改变事实时的输入、输出、权限与行为约定 |

四个视图可以合并承载，也可以分别维护；分别写完不代表整体成立。未知条件下可以标明假设做候选推演，不形成确定承诺。技术选择与调查穿插进行，不固定先选完整技术栈、最后才考虑用户操作。

**设计方法**：

1. **业务语义先行**：先明确对象及其关系、责任和状态，再设计数据结构。按钮、命令、事件和快照的时点要能追溯到业务场景，幂等和并发机制服务该时点。
2. **按任务确定交互**：考虑频率、概览、比较、切换、并行及中断，先定信息层级与产品形态，再选组件。业务流程、工作项或后台阶段不直接决定页面分区或步骤向导。
3. **对照现有行为**：关联需求和现有界面，识别满足、部分满足、缺失、冲突及无依据行为，说明继承、调整或新增理由。发现遗漏需求回到需求梳理。
4. **贯通操作与处理**：操作流程说明用户可见信息、输入、反馈、空结果、失败与恢复；实现路径说明处理责任、输入输出、状态、保存、通知和故障恢复。用户离开后继续与系统重试是两个层面的设计，围绕同一场景衔接。
5. **边界与状态有归属**：分别说明逻辑职责、运行和部署关系，不混用模块、服务和进程。长期事实、运行状态及配置有明确持有与修改责任。
6. **证据支持选型**：先检查既有成熟能力，关键路线按驱动因素比较真实候选，说明条件、取舍、证据与替换代价；不凭流行度、印象或固定候选数量作选择。
7. **核心契约先行**：语义、责任、权限、状态、幂等、事务与恢复先定，相关协作实现开始前具备必要契约；普通字段、索引和迁移细节按依赖补齐。
8. **风险驱动验证**：优先处理会改变路线的未知，外部能力定义适配、降级与失败关闭，禁止以假状态冒充成功。只建设当前范围与必要衔接。

数据时效、质量和追溯属于需求，调度、模型和存储机制属于技术选择。必要时用原型澄清高影响交互，但不为每个局部决策新增确认。命令行等非图形界面同样需要输入、输出及恢复设计；内部服务则明确调用与反馈契约。

**完成条件**：当前需求有设计支撑，核心场景四视图一致，操作、对象、状态、边界和契约清楚，关键路线有依据或明确验证安排。阻断解决或隔离，其余未决有影响与处理方式。形成方案、契约及必要决策和证据入口，自检后进入独立审计，不直接视为开工授权。

### 第三步：方案审计

**目标**：独立检查内部自洽、需求覆盖和可规划性，而不是检查文档是否齐全。

正向检查诉求和需求是否得到承接，反向检查关键设计是否有有效依据，识别技术推演引入的产品假设。沿同一场景核对四个视图，并跨材料检查范围、入口、对象、状态、排除项和验收口径。

**审计方法**：

- 用重复提交、并发、迟到结果、部分失败、越权、恢复与限额寻找实际反例，检查业务事实是否被覆盖、伪造或错误推进。
- 检查用户能否获得被要求提供的信息，是否有负担更低的替代办法；新增关键假设与默认行为必须显式呈现。
- 反证界面是否服务任务：后台步骤是否被当作用户步骤，布局是否割裂上下文或增加不必要跳转；局部样式修正不能代替交互策略调整。
- 检查关键技术候选、适用条件和证据；一个库存在、一个链接或一次成功不等于路线已经成立。
- 对可能推翻方案的未知安排短探针，只回答一个问题，限定成本、输入、时长、停止条件和授权范围。

证据记录明确对象、环境、输入、步骤、完成证据、限制及结论，部分通过说明未通过范围。问题按设计待决、证据缺口和规划补充分流，按影响分为阻断、局部回填或后续登记。常规检查由审查者完成，不要求责任人逐项签收正常项；没有检查证据不自动通过。

审查与决策分离，裁定回填权威正文，不在审计报告中另起方案，也不采用“最新材料自动覆盖”的规则。

**完成条件**：相关范围追溯无断点，阻断已关闭或从当前可规划范围中明确隔离，关键未知有足够依据或验证安排，裁定已回填。最小产物是整体结论、实质发现及影响、事项和证据引用，不复制所有正常检查项。

### 第四步：工作规划

**目标**：将方案组织成可按依赖实施、按证据验收的交付结果。

工作项说明身份、对应需求、交付目标、范围、方案依据、前置依赖、可验证验收、未决和状态。粒度停在主要依赖明确、能够独立验收的层级。功能分类、代码结构和工作项不是同一棵树，不能直接逐项复制。

**规划方法**：

- 区分方案、能力、证据、资源及验收依赖，依赖指向具体交付结果。
- 识别公共地基，并组织能够贯通业务主链路的垂直切片；按场景需要纳入真实状态、保存和恢复，避免用演示代替真实交付。
- 仅细化当前批次及依赖成熟的任务，未来工作保持规划粒度。
- 既有系统改造区分保留行为的结构调整、真实链路接入和体验优化，分别设目标与验收，避免混改后无法归因。
- 形成当前批次的目标、包含与不包含项、交接顺序、端到端验收、权限和下一批入口。

规划阶段确定工作项验收标准，实现细节可在开工前补齐。开工前检查范围与验收一致、核心交互和领域语义明确、关键能力有依据或验证安排、协作契约齐备。相关缺口未关闭时只阻塞受影响工作，不通过修改下游记录伪造前置条件。

**完成条件**：边界和验收明确、依赖无悬空、批次衔接可解释、缺口已分流。规划、排期与实施授权分别表达；规划完成不自动批准费用、迁移、部署或真实数据操作。

### 第五步：任务派发与执行反馈

**目标**：让执行者依据清晰交接独立完成工作，用证据与反馈校正方案并证明交付价值。

已具备条件且获授权的当前任务才进入实施。开工说明引用规划中的验收标准，写清任务目标、所属工作项、范围与非目标、必读依据、约束、环境权限、交付格式及停止升级条件。

**交付方法**：

- 小步交付可核查结果，记录变更、测试、运行证据、环境与限制，不用大段说明代替结果。
- 独立审查边界、需求和规范、验收覆盖、权限、并发、恢复、外部影响、占位行为及文档一致性。
- 验证环境不足时在授权内补充适用证据；样例和降级必须标识，不能冒充真实成功。
- 保留已确认行为再改结构，每步核对影响范围；将结构统一、链路接入与体验优化的结果分别验收。
- 失败先判断契约还是实现有误，不删除必要用例、放宽标准或吞掉异常制造通过；测试预期确实错误时说明并修正依据。

偏差分为修实现、回填方案、补外部证据并回归、变更需求基线四类。改变默认行为、公共契约或核心模型后，检查影响面并更新相关记录。未完成、临时限制与遗留风险不能随任务关闭消失。

**任务完成条件**：验收有证据，独立审查和必要回归完成，环境限制明确，偏差正确归口，遗留有责任及安排。

**批次业务验收**进一步回答目标角色能否在真实场景完成核心任务、最初问题是否解决、哪些路径仍受限、使用成本是什么，以及下一批应继续、调整、暂停还是补验证。技术测试通过不代替业务验收。简单批次只需保存已走通和受限场景、目标差距、继续使用条件及后续决定。

## 五、持续记录、变更与收尾

有效结论随形成及时保存，草稿和候选标明状态，不等环节全部结束才记录。每次收尾核对：依据能否定位、有效正文是否更新、问题是否有去处、状态是否准确、下一步是否有足够入口。具体承载形式由项目选择。

需求、统一语言、领域模型与方案会持续演进。发现语义歧义或模型无法表达真实业务时，回到对应依据修正，再同步受影响的设计、工作项和验收；新术语不能由局部任务临时创造后自然扩散。

现状结论、需求确认、方案确认、工作规划与开工授权是不同决定。已确认内容的实质变化应保留原因、影响和相应责任人的批准；记录历史确认不能替代当前适用性判断。

归档保留重要决策背景、交付证据和必要变更历史，移出失效、重复及已被替代的过程内容。清单、摘要和报告都不能成为另一套竞争事实源。收尾的判断依据是业务问题、决策和交付是否形成闭环，而非文件数量或任务勾选数量。
