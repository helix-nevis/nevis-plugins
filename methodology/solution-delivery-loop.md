这套流程的主线是：**先知道“我们现在有什么”，再统一“我们在说什么”，然后决定“要做什么、怎么做”，最后通过执行证据持续校正。**

流程不是严格单向的。后续步骤发现前置结论不完整时，应回到对应步骤补充，但不能跳过确认直接修改既定结论。

本工作法的目的不是增加文档和人工审批，而是**把影响执行的不确定性逐步转化为已对齐、可验证的结论**。智能体依据明确边界推进常规工作，人只处理必须由人判断的事项，从而减少偏差、提高验收通过率、减少返工。

## 一、产物怎样才真正有效

一个内容只有满足以下条件之一，才值得进入长期产物：

- **执行依赖**：后续实施必须据此工作；
- **验收依赖**：判断是否完成必须引用它；
- **决策依赖**：缺少它会重复争论或改变重要取舍；
- **变更依赖**：后续修改需要知道影响和依据。

不满足这些条件的中间讨论、失败尝试、临时判断和重复日志，可以保留在过程记录或归档，不进入长期阅读入口。

### 1. 一套正文，分层阅读

人工阅读和智能体执行使用同一套事实源，不维护两套平行正文。文档按“概述—核心内容—规则与细节—追溯”自然组织：人通过概述快速判断方向，执行者按任务读取相关章节和契约。

### 2. 摘要、事实与证据分层

- **摘要**帮助快速理解，引用事实，不另立口径；
- **正文**保存当前有效结论；
- **证据**说明结论如何得到，保留环境、限制和来源。

证据和过程记录不能反向覆盖正文。事实发生变化时，应按对应权限更新正文，再保留必要证据索引。

### 3. 项目资料分区与正式产物

建议在项目工作目录下使用 `.proj/`，先复用已有权威位置，不机械迁移或复制：

```text
.proj/
├── README.md                 # 导航、当前入口与关键缺口
├── sources/
│   ├── INDEX.md              # 来源与资产索引
│   ├── messages.sqlite3      # 已安装捕获 Hook 时自动维护
│   └── files/                # 外部原件及必要快照
├── inbox/                    # 尚未完成归类或路由的信息
├── working/                  # 草稿、分析与辅助理解材料
└── artifacts/
    └── project-profile.md    # 项目背景、有效约定及相关入口
```

这是职责结构，不要求预建全部空目录或文件。盘点按需补齐导航、项目档案与来源索引；后续需求、方案、工作规划、统一事项及交付证据在 `artifacts/` 中按需建立，已有等价位置则引用。独立 `discovery.md` 或 `technical-baseline.md` 仅在内容有独立阅读价值时拆分，短盘点结论可留在项目档案。

### 建档与资料归属

- **项目档案**保存项目身份、业务背景与目标、本轮任务、职责、有效约束及相关入口；项目长期目标、本轮完成标志和实际状态分别表达。技术、需求、环境规则已有权威位置时引用，不复制正文。
- **来源与资产索引**记录名称与类别、位置、用途线索、判断依据及重要疑点。整体声明覆盖边界与读取深度，个别深入项单独注明，不逐文件写摘要或逐条重复“未运行”。后续调查获得新证据时更新对应项。
- **sources/files/** 保存外部交付原件和确有必要的固定版本快照。既有代码、有效文档和会话原文通常保留原位置，只登记引用；原件不随分析结论改写。
- **inbox/** 只暂存未完成归类或路由的信息。已经识别的需求、冲突、待决策或待验证事项进入对应正式产物并标明状态，不能因“未确认”长期滞留 inbox；路由后清理暂存或保留指针，避免双份正文。
- **working/** 保存草稿、推演、比较和辅助材料；形成有效结论后回填正式产物，过程材料按需要归档。
- **artifacts/** 是正式维护位置，不表示所有内容都已确认；事实、候选、有效约定和未决内容应明确区分，确认时更新原位置，不靠搬文件表达确认状态。

`.proj/` 只有消息数据库时尚未完成建档；检查档案内容并增量补齐，不重置或覆盖数据库。没有捕获 Hook 时不要求手工创建数据库。Hook 仅登记来源，不做语义分类；后续实体与结论在内容侧追加来源引用，不向消息索引写业务关联。只有取得可靠定位信息时才引用具体消息编号，不编造 `capture_id`，也不为归档重复抄写会话原文。

### 4. 四类贯穿信息的唯一归属

需求梳理维护客户诉求清单、独立统一语言与需求文档；需求项引用诉求，诉求引用原始来源，具体最小内容按第一步组织。

| 信息 | 权威位置 | 其他环节如何使用 |
| --- | --- | --- |
| 待澄清、待决、冲突与验证事项 | 统一事项清单 | 发现时登记，阻塞处引用，关闭时回填正文 |
| 统一语言 | 独立共享产物 | 方案、契约、工作项和任务统一引用 |
| 追溯关系 | 下游引用上游依据 | 诉求引用原始来源，需求引用诉求或约束，方案引用需求，工作项引用需求与方案，交付引用工作项与证据；按引用反查覆盖 |
| 重大决策 | 决策记录，只追加 | 正文引用结论，记录保留背景和权衡 |

不要在每一步分别建立待决台账、验证台账和完整追溯矩阵，形成多个互相竞争的事实源。

## 二、讨论与落实的基本节奏：总—分—总—分

每个环节都采用同一节奏：**先整体对齐，再分点对齐；先形成整体结论，再分点落实。** 对齐首先是确认双方讨论的是同一个问题、同一层目标和同一组边界，不是一开始就对所有答案达成一致。

1. **先整体对齐**：说明为什么讨论、要解决什么、处于哪个层次、什么已确定、什么不在本轮范围。可以提出结构草案供校正，但不能把所有细节当成既定事实。
2. **再分点对齐**：逐项处理关键分歧，区分事实、假设、建议和待决定内容，说明选项、依据、代价和影响。依赖未定的子问题延后，不强行拍板。
3. **回到整体形成结论**：重新检查目标、范围、核心规则和各部分关系，避免把零散回答直接拼成最终方案。整体确认前，单独列出新增关键假设、默认行为和用户新增负担；整体确认不等于确认未显式说明的关键默认值。局部修正后要重新校验整体，不因解决当前暴露的问题就恢复实施或继续细化下游方案。
4. **最后分点落实**：分别更新术语、需求、方案、决策、验证事项和工作项，保留结论与修改位置的对应关系。

每轮讨论都应回答：**整体是什么，本轮对齐哪些点，合并后的结论是什么，结论分别落到哪里。** 整体未对齐时继续澄清，不用细节数量制造确定性；整体结论未确认时，不进入全面实施。

## 三、默认推进，异常升级

事实查证、资料整理、常规设计修正、自动检查、测试执行、状态更新和证据整理由智能体默认推进，不要求人工逐项审核。

只有以下事项需要升级：

1. 目标、核心范围、需求文档中已确认要求和验收承诺的变化；
2. 重大方案取舍、公共契约和关键技术路线；
3. 费用、账号、真实数据、外部写入、迁移和部署等授权；
4. 无法自行消解的矛盾及高影响未决事项；
5. 批次验收结论，以及是否进入下一批。

**不逐项人工审核，不等于不逐项分析。**智能体先在内部细致扫描事实、识别假设、推演场景、比较替代方案，并检查用户成本和返工影响，再减少对外提问。默认推进有依据、低影响且可逆的常规工作，不是未经审视的关键假设；智能体负责把细节想透，人只处理真正需要人决定的取舍。

“默认推进”不等于无限授权，“人工判断”也不等于逐条审批所有常规内容。若人工接触点远超上述五类，通常说明目标、边界或产物仍未写清，而不是审核得不够。

### 委派与上下文

讨论进行到一定阶段后，上下文会因大量阅读而膨胀：盘点要读几十份资料，审计要复核长文档，这些原文一旦留在主对话里就会一路累积。把这类工作交给子智能体、只带回结论与证据索引，能显著减轻主对话负担。

但**委派应按工作性质切分，不能按环节切分**。同一环节中，读取和判断性质不同：调查、证据判断、候选比较与建议可以委派，用户确认、重大约定变更及整体整合由主线程组织。按环节整体委派，会迫使子智能体替用户做决定，或让主线程只能凭摘要重建全貌。

是否委派由两条判据决定：

1. **压缩比**：读入量应显著大于返回量。读三个文件却返回两页结论，通常只是把上下文换成转述。
2. **歧义能否静默上报**：遇不确定可记录下来交回主线程的可以委派；必须当场询问用户才能继续的留在主线程。本工作法将用户澄清集中在主线程，子智能体返回歧义及影响，不猜定或代为确认；具体交互能力取决于工具与运行方式。

据此，大范围盘点可委派目录与清单扫描，小范围索引直接完成，不默认深入或运行；方案审计适合独立委派，且受益于未参与设计的视角。需求梳理可委派按调查问题收集素材、候选诉求及出处；基线综合、多轮递进澄清和用户确认留在主线程。方案设计可委派现状核对、技术候选比较、接口取证和四视图交叉检查；产品形态和重大取舍的最终整合、用户确认及整体一致性由主线程组织。工作规划可委派机械推导，范围判断与批次排序由主线程把关。执行按开工说明派发。

**需要用户确认的问题，不得由子智能体自行决定，也不得代为确认。**

委派必须约定返回内容：结论、出处、证据状态、未覆盖范围和待决问题。只回“已检查，无问题”的委派不合格，它用上下文换来了不可核验的断言，比上下文堆积更难发现错误。主线程据此逐项核对，而不是照单全收。

主线程始终保留与用户的完整对话、统一语言当前状态、关键取舍及理由、权威正文写入权和整体校验。**整体校验不能由子智能体摘要拼成**，那会把“总—分—总—分”的第二个“总”降级为重新汇总零散结论。

还要防止矫枉过正：压缩比不足、必须当场判断、或结论与过程体量相当的任务，不要起子智能体。子智能体缓解上下文压力，但不修复读取纪律；任务说明里仍要写明只读高信号入口、返回索引而非全文，否则庞大的读取只是换个地方发生。

## 第零步：项目建档、信息收集与现状索引

### 1. 职责与执行顺序

盘点以建立资料和能力索引为主，回答项目是什么、本轮解决什么、相关入口在哪里、已有依据到什么程度，以及下一步还需调查什么。覆盖本轮相关来源和主要区域，不要求读取全部内容或实际运行。

按“识别已有档案 → 提取当前已知信息 → 补齐最小结构 → 扫描并建立索引 → 针对缺口补问 → 更新档案与下一步入口”推进。新项目同样可以建档，没有代码时记录已有背景和资料入口，不强凑技术信息。

先复用已有权威文档，不机械迁移或复制。`.proj/` 可能只有 Hook 创建的消息数据库，不能据此认定已建档；检查项目档案及当前任务必需信息，已有则按需补充，缺失则建立，保留原有数据。目录与产物归属见下述产物组织规则。

### 2. 值得收集的信息

只收集会改变项目理解、执行方式或完成判断的信息；以下是按需覆盖的类别，不是初始化必填表。

| 信息组 | 收集内容与入口 |
| --- | --- |
| 项目身份与位置 | 名称、简要说明、项目目录、仓库、代码与文档入口 |
| 业务背景与目标 | 使用对象、场景、当前做法、主要困难、期望结果 |
| 本轮任务 | 当前问题、交付内容、完成标志、范围与排除项；与项目长期目标分别记录 |
| 当前状态 | 已有构想、原型、实现及实际使用情况，注明依据与不确定性 |
| 来源资料 | 客户资料、需求、设计、原型、历史决策、验证记录的位置、版本或时间及有效性线索 |
| 已有能力 | 业务模块、接口、工程设施、公共组件、内部工具和可复用资产的入口 |
| 技术基础 | 语言、运行时、框架、数据库、构建测试工具，关键第三方库、开源框架与外部服务的版本和用途线索 |
| 技术实践与经验 | 项目规则、开发测试发布方式、历史尝试、放弃原因、已知限制及经验出处 |
| 职责与约束 | 业务确认与验收职责、已有承诺、实际存在的时间资源限制、必须保留的行为 |
| 执行条件 | 运行命令、环境入口、可修改范围、验证条件与操作边界；在相关执行前补齐 |

技术信息优先从目录、依赖清单和项目规则获取，只索引影响当前工作或可能复用的关键项，不逐项抄录全部依赖；完整版本以清单和锁文件为准。区分项目已采用的技术、其他项目的可复用资产与经验、为当前需求新发现的技术候选；历史成功不自动证明当前适用，候选不写入既有技术栈。

项目阶段、目标、资料有效性和复用判断不能仅凭目录名、提交数量或依赖存在推定。初始化日期只能说明建档时间，不能默认是项目启动日期。凭据只记录配置位置，不收集或写入明文。

### 3. 索引优先与读取深度

采用满足当前判断所需的最浅读取深度，上一层足够时不进入下一层：

| 深度 | 动作 | 深入条件 |
| --- | --- | --- |
| 目录与文件名 | 识别区域、资料类别和可能的能力入口 | 尚不能分类或定位 |
| 清单与元信息 | 查看依赖、配置、标题、目录和版本 | 尚不能判断范围、关联或有效入口 |
| 关键片段 | 定向搜索和读取相关内容 | 当前重要判断仍缺依据，或来源存在冲突 |
| 专题调查与验证 | 深入代码、跨资料分析，必要时实际运行 | 下游工作确实依赖更强证据，另行明确问题、范围和验证条件 |

不默认启动项目、执行构建、跑测试或探测接口。只发现测试目录就登记测试资产入口；只发现认证目录就登记认证相关代码候选入口；依赖清单声明框架只证明声明存在。

索引记录名称与类别、位置、用途线索、判断依据，以及重要疑点。整体说明覆盖边界与读取深度，个别深入项单独注明；不为每个文件生成摘要，也不逐条重复“未运行”。索引服务后续按需读取，不直接生成已确认需求。

页面先登记路由、菜单、页面目录等可发现入口。只有具体需求或专题调查需要时，才沿“整体功能地图—单页功能—关键功能的数据、接口、状态与证据”深入，并从权限、异常、恢复和目标反查遗漏；该链路不是每次盘点的默认任务。前端可提供业务、代码与验证资产线索，但不自动证明需求或布局正确。

### 4. 候选、证据与补问

直接观察的事实注明出处；推断标明依据与不确定性；资料中的目标和历史约定先作为候选检查有效性。当前消息已明确的信息直接采用，不重复询问。

以下证据层级只描述已有依据，不要求盘点逐项完成三级核验：

- **存在**：有文件、代码、配置或文档记录；目录只证明入口存在。
- **可用**：有适用场景的实际运行或验证依据，注明范围和时间。
- **可承诺**：能力、授权、成本和稳定性足以进入特定交付范围，不能由盘点自行认定。

已有验证记录就引用，没有就停留在当前层级；不因未验证而给所有资产创建验证任务。只有影响后续判断的缺口才登记问题、影响和调查入口。静态存在不能推导可用，单次成功不能推导交付承诺。

使用 AskUserQuestion 收集无法自行查明且影响推进的背景、冲突与约定。每轮围绕一个主题提出少量相关问题，候选说明依据，允许 Other 自由填写及“暂不确定／稍后补充”；不为凑选项预设业务目标。不逐字段确认，也不通过整组确认把所有推断升级为事实。已有明确回答直接写入，仅对重要歧义继续追问。

先收集足以确定盘点位置和范围的信息，扫描后再补问。运行环境与操作条件在相关执行前补齐；缺失信息只阻塞依赖它的工作。新输入与档案不一致时，区分历史失效、描述错误、范围不同和需求变更，不静默覆盖，也不一律视为变更。

### 5. 完成与后续衔接

完成条件：项目背景与本轮任务足以支持下一步；相关来源和能力入口可查；覆盖边界及证据深度清楚；关键缺口、冲突和调查入口已有去处。无需证明所有能力可用或完成全部复用判断。

项目档案与来源索引是最小产物，复用已有等价位置即可；独立盘点报告、技术基线和验证记录仅按需产生。需求梳理、方案设计或执行中沿索引调查相关内容，新增证据回填原位置。现状说明现在有什么，需求说明决定做什么，方案说明怎么做，当前批次说明本次交付什么，四者不能混用。

## 第一步：需求梳理与统一语言

### 1. 来源与调查循环

来源包括用户当前输入、文档、现有界面（原型、截图或实际系统）和对话历史。代码、接口、样例数据与验证记录是解释现状和核对约束的辅助证据。来源中要区分目标、诉求、当前做法、业务规则、方案建议、技术实现与隐含假设；现有界面只说明当前怎么做，历史讨论中的候选不自动成为当前结论。

按以下循环推进，不一次提取后整组确认：

1. 从盘点索引定位相关资料，整体理解目标、角色、场景与业务流，形成有出处的候选诉求。
2. 建立持续的需求调查问题清单，检查谁在什么情境下做什么、输入如何取得、责任与规则、结果、异常及完成判断。
3. 带着问题定向查阅材料，找到答案就记录结论与具体出处，不无目的通读。
4. 查不到、来源冲突或必须由业务方取舍时，用 AskUserQuestion 少量分批提问；已有答案不重复问。
5. 根据答案补充新问题，继续调查、推演与澄清，不能将启发型问题自动升级为新增需求。
6. 回到整体业务流校验遗漏、矛盾、关键默认值与用户负担，整理诉求并转译为需求文档，对核心范围和关键取舍作必要确认。

问题分澄清型（歧义与边界）、启发型（遗漏与反例）、确认型（关键取舍）；复用统一事项清单，不另建重复问答台账。只保存问题、关联诉求或场景、结论及来源、状态与影响、回填位置，不复制全部问答。影响当前核心范围和基线的问题须解决、排除或明确隔离受影响范围；其他问题说明安排，不要求全量清零，也不能只登记就绕过阻断。关闭后回填诉求、统一语言或需求正文。

### 2. 诉求转译与需求表达

客户诉求清单保留用户意图及澄清、处置结果，需求文档组织当前业务要求，统一语言独立维护共享语义。需求项引用诉求项，诉求项引用具体消息、文档章节或界面位置；法规、外部契约与明确约束可直接成为需求依据，不虚构客户诉求。

表达不同而意图相同的诉求可合并并保留多源；一条诉求可拆成多项需求，多条诉求也可支撑同一需求。保留不采纳、暂缓、否定或替代的必要原因，不静默删除。确认状态、重要程度和本期是否纳入分别表达；核心性、优先级和迭代不能绑定。

功能需求表达骨架：**在什么场景下，哪个角色需要系统提供什么行为，遵守什么规则，得到什么可观察结果。**至少有稳定编号、名称、描述、依据与验收；规则、边界、异常和质量要求按实际需要补充或引用。避免“正常运行”等不可判定验收，不强迫每条需求套长表。

例如：FR-012 查看趋势简报——店主准备企划时，可以查看所选市场与时间范围的简报，识别覆盖期与更新时间并追溯关键结论的依据；无符合条件的内容时明确告知。引用对应诉求与约束，以范围、新鲜度和依据可识别作为验收点；允许延迟多久未确定时，保留具体问题，不自行填写数值。

按业务能力或功能域分组，层级按复杂度展开，不强凑四级，不默认新增与需求重复的功能编号。成本或可行性信号仅标记具体未知及影响，不据技术名词推定工作量；统计、报价和复用系数不是通用必填项。

### 3. 轻量统一语言

| 字段 | 要求 |
| --- | --- |
| 规范名称 | 后续统一使用哪个词 |
| 简短定义 | 概念是什么，不描述系统实现 |
| 非等价词 | 哪些近义词不能混用 |
| 边界与反例 | 什么不属于这个概念 |
| 当前状态 | 已确认、暂定或存在冲突 |

术语一经澄清立即记录，不等讨论结束统一整理。用具体场景检验边界，例如“完成”指生成成功、用户采纳还是业务定稿，“保存”指暂存、文件落盘还是正式入库。

资料或代码能回答的问题先自行查证。口头描述与代码行为不一致时，区分“当前实现如此”和“目标业务应当如此”，不能由其中一方自动覆盖另一方。

### 4. 从信息到候选需求

先区分业务目标、用户任务、业务规则、当前做法、方案建议、技术实现、隐含假设和待决与待验证事项，保留出处。文档写了、代码存在或行业常见都不能单独证明需求成立；“做一个卡片”是方案候选，“用户据此识别问题并完成判断”才可能是需求。

按“事实地图—核心角色与高价值主线—场景合并证据—候选需求—内部推演—整体基线”推进。同一需求可能分散在文档、原型、代码和会议记录中，先跨来源组合，再检查来源、冲突、角色、对象、条件、结果、用户负担、反例和替代方案。详细扫描由智能体完成，不把每个小问题都抛给用户。

登录、身份识别、组织归属、权限、角色和进入条件属于需求，不是可默认套用的技术设施。凡要求用户提供内部标识、额外信息、专业知识或前置准备，先判断用户如何获得、是否必要、系统能否自动取得，以及是否有更低负担且不改变业务结果的替代方案。关键默认值未确认时不得作为基线进入开发。

### 5. 需求三维判断

- **重要程度**：核心、非核心或明确不做；
- **明确程度**：已经想清楚或仍有歧义；
- **确认方式**：讨论可确定，或必须依赖调研、测试和外部条件。

目标、规则和优先级不清时向业务方提问；外部能力不清时登记验证，不用讨论代替验证。暂时不能确认但不影响整体设计的，可带假设推进；影响核心范围的，暂停相关设计。

### 6. 六种需求方法

1. **决策树访谈**：先给出问题全貌和决策主干请对方校正，再展开前置条件已明确的问题。对核心候选需求围绕目标、真实场景、责任、边界、异常和替代方案多轮递进反问，每轮依据上轮答案继续推演，不一次抛出完整问卷，也不只重复“是否确认”。每题给出建议、选项和代价，事实先自行查证；分点完成后先汇总整体理解，再写入基线。
2. **场景推演**：一次验证一个真实问题，从高频主链路沿“触发—输入—业务对象—责任动作—结果—异常恢复”走查。先确认用户如何发起、控制和完成核心任务，再讨论实现机制。对全局入口、核心操作方式、身份权限、核心对象或主流程等高影响原则，用端到端场景和具体界面说明实际行为、影响范围与替代方案，再请求必要确认；文档写过、历史确认过或整组原则获确认，不能替代对高影响结论的有效对齐。没有业务依据的低频分支只登记，不展开。
3. **边界追问**：用正例、反例和极端情况澄清从何时开始不算、失败后算什么、重复操作怎么办、谁有权推进和是否允许后补。
4. **责任分离**：对关键动作确认谁提出、谁决定、谁执行、谁留痕，不让普通消息或系统返回结果替代明确的业务动作。
5. **反向排除**：区分当前阶段不做与永久不需要，避免后续专项被误删或提前塞入本期。
6. **编号追溯与冻结检查**：编号发布后不因排序变化重排；冻结前集中处理核心口径、范围、指标和验收影响，普通页面细节不阻塞整体基线。

本步形成客户诉求清单、独立统一语言与需求文档。需求文档包含目标、场景、业务流程、功能、规则、质量、约束、范围、验收及迭代范围；需求文档中的确认基线是其中已确认的有效要求。

## 第二步：方案设计

### 设计入口与协同推进

先引用需求文档及有效基线、独立统一语言、业务流程、项目档案和现状资产索引，明确本轮设计范围与排除项。按当前问题读取相关内容，不把建档重做一遍。业务流程独立于拟建工具，关键活动须说明目的、所需信息、核心关注、角色责任、结果及异常，不能仅用箭头代替。

在方案概述中提取设计驱动因素，不另建重复参数文件：

| 驱动因素 | 需要明确的内容 |
| --- | --- |
| 硬性约束 | 必须满足什么，引用具体上游依据 |
| 关键质量要求 | 时效、性能、可靠性、可追溯性等如何影响当前设计 |
| 系统与集成边界 | 外部角色、系统、数据源与服务分别承担什么责任 |
| 规模与使用条件 | 用户、数据、并发、部署和维护条件；区分事实与规模假设 |
| 关键取舍 | 当前真实存在的目标冲突、代价及影响 |
| 关键未知 | 可能推翻方案的问题，调查或验证安排及阻塞范围 |

需求不完整时可以做候选推演或技术调查，但必须标明假设，不形成确定承诺；必要澄清只阻塞依赖它的设计，其他部分可继续。已有有效答案不重复问，不逐项询问抽象质量偏好。影响目标、核心操作、公共契约、成本、部署或维护方式的重大取舍，先给依据、候选和代价，再用 AskUserQuestion 确认；普通选择由智能体推进。

按“设计依据 → 核心场景 → 协同设计 → 调查、验证或提问 → 场景回检 → 整理有效结论”循环，不固定先完成全部技术栈、再架构、最后才设计用户操作。

| 设计视图 | 核心内容 |
| --- | --- |
| 领域与业务状态 | 对象身份、关系、责任、规则、生命周期、状态与长期事实 |
| 产品与操作流程 | 产品形态、信息层级、入口、动作、自动行为、反馈、结果与恢复 |
| 系统架构与实现路径 | 系统边界、子系统与模块职责、协作、处理路径、状态归属与部署 |
| 数据与接口契约 | 保存的事实、数据关系与存储分布，边界输入输出及行为语义 |

四个视图围绕同一场景按依赖细化，分别引用需求，关键选择说明依据；不是四份文档各自写完就视为整体成立。适用范围很小时可合并表达，没有人机操作的内部服务可省略界面部分，仍保留调用和反馈契约。

### 需求、交互与技术的衔接

需求明确用户任务、业务行为、规则、质量和可观察结果；交互设计明确入口、页面、操作路径、反馈及用户中断后的继续方式；技术方案说明系统结构、边界、职责、选型、部署、契约及为满足需求所需的内部实现路径。实现路径是技术方案的一部分，描述信息和控制在系统内如何流转。技术可行性调查可以提前，但不能替业务方决定规则。数据新鲜度与历史追溯属于需求，更新调度和存储机制属于技术方案中的实现路径；分析质量要求不自动等于必须采用 AI。系统故障恢复与用户取消、离开后继续分属技术方案和操作流程，需在同一失败场景下衔接。

交互方案引用需求项及现有界面依据，对照已满足、部分满足、缺失、冲突和无需求依据的行为，决定继承、调整或新增。现有按钮和字段不自动成为必须保留的需求；发现遗漏时回到需求梳理，不由设计者静默补定。业务功能分组不等于技术模块或交付工作项，一项需求可跨多个模块，一个模块也可支持多项需求。

统一语言在本步发展为领域模型：术语回答“在说什么”，概念关系回答“如何关联”，领域模型回答“对象如何构成业务”，接口与数据模型回答“系统如何交换和保存事实”。

领域模型至少明确核心实体及身份、关系与边界、生命周期与状态转换、创建和修改责任、必须长期保存的事实，以及不同上下文如何引用。

### 1. 业务事实优先

从业务动作反推必须保存的对象、关系、输入快照、操作人和结果。页面是事实的视图，不为每个页面复制状态。先区分核心对象及其关系，再选择统一或分离的实现模型；业务语义未对齐时不得先比较表结构和存储方案。

命令、按钮、任务、事件和快照都隐含业务时点及责任，必须追溯到已确认场景。输入快照、幂等、版本和并发机制服务于该业务时点，不得反过来决定用户如何操作。

### 2. 交互策略与布局决策

涉及界面时，先检查已有页面、原型、截图、设计系统、组件规范和典型任务，提取明确原则与实际惯例，分别标注**可继承依据、存疑做法和明确反模式**，注明来源。现状是证据，不是设计正确性的证明；无法判断某项做法是业务约束还是历史偶然时，先追溯来源，仍不能确认再提问。

先回答用户的主要任务、工作频率、全局概览需求、比较与反复切换、并行处理和中断恢复，再明确主对象、主操作、核心状态及常驻与按需展开的信息。据此选择工作台、列表—详情、主从视图、编辑器、看板或向导等产品形态，再选择组件。

**流程描述业务推进关系，不直接决定页面结构。**步骤数量、工作项数量和后台处理阶段都不是页面分区依据。只有顺序严格、上下文少且需要明确引导时才考虑向导；需要跨阶段理解、比较或反复切换时，优先论证整体工作区、列表—详情等非步骤式结构。卡片只用于确有必要的并列摘要、独立实体或离散操作入口。

不泛泛询问“设计原则是什么”，先给出有依据的推荐、备选和代价。以下情况必须请用户确认：现有前端与任务目标冲突；现有依据缺失或相互矛盾；存在多种高影响产品形态；需要改变整体导航、核心操作习惯或视觉方向。局部组件、间距和常规样式按已确认规范默认推进。用户要求保留存疑现状时，记录约束及代价，不将其写成合理设计原则。

在《产品交互方案》中增加“交互原则与布局决策”一节，记录设计依据、核心任务、选定形态及原因、信息层级、主操作路径、关键取舍和明确避免的模式，不另建长文档。

### 3. 页面功能与真实链路设计

关键页面功能逐项说明用户目的、数据来源、时间与业务口径、处理责任、需要长期保存的事实、接口返回、输出结果、刷新方式和异常。区分业务规则与技术实现，不能只写“调用接口”或“生成内容”；数据不完整、结果能否追溯、保存与重新生成规则必须有明确位置。

关键按钮先定义业务动作，再定义请求：创建什么对象、携带哪些必要上下文、生成草稿还是正式结果、谁可修改与确认、同步或异步、重复操作、失败恢复、离开后继续和权限如何处理。不能用“点击后调用接口”替代这些判断。

现有前端重构时，页面通过接口层与后端和样例数据隔离，假数据不得散落组件或冒充真实成功。组件、全局样式令牌、路由和状态管理按真实复用与一致性需要提取，不为组件化过度拆分；已确认的行为由测试或必要基线保护。

### 操作流程的完整表达

每条核心操作流程说明入口与前提、用户可见信息、输入与动作、系统自动行为、加载与成功反馈、空结果与失败反馈、最终业务结果，以及取消、重复操作、中断和恢复。步骤列表可辅助表达，但不能只有点击顺序；一个业务活动可有多种操作流程，一次操作也可支撑多个业务活动。

CLI 同样需要设计输入、输出和恢复，不因没有图形界面跳过交互。按本轮需求及必要衔接覆盖流程，不只按优先级标签选择。已有视觉规范优先引用；缺少依据且影响整体形态或使用习惯时才确认方向，不强制画完整原型，必要时引用线框或原型文件。

### 系统架构与技术取舍

架构分别说明逻辑职责、运行进程与部署单元，图中标明边界类型，不把子系统、模块、服务与进程混作同一层次。每个主要单元说明做什么、不做什么、承接哪些需求、与谁协作；代码位置仅在已有或确需确定时引用，不用目录划分代替职责设计。

用核心场景说明实现路径：输入从哪里来、由谁处理、产生什么业务事实、保存在哪里、如何返回或通知、失败如何处理。分别明确持久业务事实、运行时状态和配置的持有者、修改责任及恢复方式。逻辑、通信与部署视图保持一致。

技术选型以设计驱动因素为标准，先核对既有技术与可复用能力；对有真实取舍的关键路线比较候选，记录推荐、排除理由、适用条件、证据和待验证部分，必要时给替代路径。常规成熟依赖不为凑数强列候选，不逐维度审批；不设固定组件数量上限，也不将单体、前后端分离、事件驱动、管道当作同一维度的互斥模式。技术性能、成本和兼容结论须有适配条件的资料或验证依据，不能用流行度、示例数字和技术印象定案。

### 4. 状态机与故障矩阵

对核心对象列出推进、失败、超时、取消、重试和迟到结果；对外部依赖列出不可用、重复响应、部分成功、限额和恢复方式。逐格确定允许行为和用户可见反馈。

### 5. 风险驱动设计

优先做深身份权限、核心标识、事务并发、文件生命周期、外部副作用和恢复路径；普通展示和非关键字段后补。区分必须现在确定的约束与可以替换的组件。风险在设计全程发现并复用统一事项记录，说明具体未知或触发条件、影响的需求与设计、已有及缺少的证据、缓解或验证安排、剩余风险和阻塞范围；只记实际相关项，不为完整性堆砌通用风险。

### 6. 适配边界与降级

外部服务通过稳定接口接入，定义正常、降级和失败关闭路径。未经验证的能力不进入核心承诺，不用静态结果或假状态冒充真实成功。

### 7. 多线交叉走查

用同一业务场景贯通流程、领域、交互和技术。冲突先登记位置和影响，再裁决并同步修改，不直接采用“最新修改版本”。

### 8. 现成优先与最小实现

优先复用经过验证的成熟能力，自研集中于真正有业务差异的部分；记录版本兼容、供应商锁定和替换成本。只建设当前范围和必要衔接，不为想象中的未来提前搭平台。

### 9. 核心契约先行

方案阶段明确核心业务语义、责任、权限、状态、幂等、事务和恢复；优先覆盖前后端、跨模块协作、并行开发和外部集成边界，说明调用方向、输入、输出、错误与相关行为条件。先有领域语义，再决定持久化，不由名词直接推导表结构。普通字段、完整请求响应、索引和迁移细节可在对应工作项开工前补齐，但不能在必要协作契约缺失时开始相关实现。

接口设计定义外部如何读取和改变事实；数据库设计定义事实如何可靠保存。机器可读契约可由 OpenAPI、Schema 和迁移文件承载，Markdown 解释业务语义和约束，避免重复所有字段定义。

### 设计自检与交接

整理当前有效方案与阅读入口：本轮范围、上游依据、驱动因素、各视图位置、关键决策、证据及未决影响。先检查当前需求是否有设计支撑、同一场景四视图是否一致、核心操作与对象责任状态是否明确、架构通信是否具备必要契约、关键路线是否有依据或验证安排。阻断项解决或隔离后再交独立审计，其他待定说明安排，不以 TODO 全部清零或文档齐全作为完成标准。

不默认另造汇总 YAML；有真实机器消费者时才定义结构化契约，指定权威位置，其他正文引用而不维护重复口径。设计自检不代替第三步独立审计，设计确认不等于规划通过或开工授权。

方案概述保存设计范围、上游依据、驱动因素、四个视图入口及未决影响。各视图按内容合并或拆分，不预建空文档，不默认生成全量汇总 YAML。独立审计沿场景检查四视图、逻辑与部署关系、关键通信契约及选型证据；规划引用相关章节，详细契约在对应实现开工前补齐，缺失时只阻塞相关工作。设计取证与候选分析可按问题委派，主线程整合场景、确认重大取舍；过程检查不能替代独立审计。


## 第三步：方案审计

对候选方案进行独立检查，而不是只检查文档是否齐全。审计覆盖：方案内部是否自洽，需求是否完整覆盖，方案是否具备规划条件。

审计采用**默认通过、异常升级**：常规一致性和覆盖检查由智能体完成，只把矛盾、缺证据、重大取舍和不可规划事项提交责任人，不要求人工逐项打勾。

问题按性质分流：

- **设计类**：进入统一待决项，由责任人决定；
- **证据类**：进入验证事项，通过资料、原型、测试或真实环境解决；
- **规划类**：在工作拆解时补充，不影响整体方案的可延后。

按影响区分阻断、局部回填和后续登记。**审计坚持审查与决策分离**：审查者可以判断不一致、缺证据或不可开工，但不能自行改变业务目标、核心范围、重大技术路线和验收承诺。

可能推翻核心方案的未知，不应等完整审计结束才处理，应尽早启动低成本**短探针**。

### 执行方法

**1. 双向追溯：需求向实现查，方案向来源查。** 正向检查需求是否有流程、交互、技术和验收入口；反向检查关键规则是否追溯到需求或明确决策，识别由技术推演悄然引入的产品假设。同时检查用户被要求提供的信息是否可获得，是否把内部实现概念转嫁给用户，系统能否代替用户判断，是否有更低负担且不改变业务结果的方案。跨文档对照当前批次范围、核心入口、对象定义、状态推进、排除项和验收口径；冲突关闭前不得通过引用“最新版本”或继续修改下游文档绕过。检查影响架构、成本、隐私、部署或体验的关键技术能力是否已有适配需求的候选和证据或验证安排；只有技术名词、候选链接或库存在不等于选型完成。

**2. 对抗性案例审查：专找实际会错的情况。** 围绕重复提交、并发推进、迟到结果、部分失败、越权、恢复和限额构造反例，检查业务事实是否会被覆盖、伪造或错误推进。

**3. 布局反证：检查页面是否服务真实任务。** 检查是否把业务流程直接画成步骤卡片、把后台阶段误当用户步骤、用重复分区割裂信息层级，或迫使用户频繁滚动、跳转和返回。去掉卡片容器后布局逻辑仍应成立。现有页面与设计原则冲突时，不因现状存在而判为合理；涉及整体形态或核心操作习惯的变化，提交带依据的候选由责任人确认。

**4. 证据卡：把验证目标写成可执行记录。** 明确对象、环境、输入、步骤、完成证据、限制和结论；一个成功案例不能代替整组能力，部分通过必须列出未通过范围。

**5. 短探针：先验证最可能推翻方案的假设。** 限定问题、成本、输入、时长和停止条件，只回答一个关键未知；探针结果进入证据层，重要结论再回填正文。

**6. 分级闭环：区分阻断、回填和登记。** 阻断问题关闭前不得实施相关工作；局部问题明确回填；纯优化和未来事项登记。完成条件是问题已解决或有明确安排，不是会议已召开。

**退出检查：** 核心需求双向追溯无断点，阻断问题已关闭，关键假设已有证据或验证安排，裁定已回写，剩余事项不妨碍规划。

**最小有效产物：**

1. 一个短审计入口和整体结论；
2. 实质异常及影响，不复制所有正常检查项；
3. 统一待决项、验证事项及证据索引；
4. 回填后的需求、方案和追溯关系。

## 第四步：工作规划

把已对齐方案组织成可以按依赖实施、按证据验收的工作，并明确哪些现在可以开始，哪些仍需等待。

**工作项不是越细越好，粒度停在“主要依赖明确、能够独立验收”的层级。** 工作项是规划层的可独立交付能力；开工前的执行任务才是实施层的具体工作。一个工作项可以包含多个执行任务，不必提前细化未来全部任务。

每个工作项至少说明：编号与名称、对应需求、交付目标、范围边界、方案依据、前置依赖、可验证验收标准、未决约束和状态。规划阶段形成与工作项边界相称的验收标准；实现细节可在开工前补齐，但实施开始前必须引用已确定的验收标准。工作项只引用权威正文，不复制需求、方案、接口或数据库内容。

依赖分为五类：**方案依赖、能力依赖、证据依赖、资源依赖、验收依赖**。分层用于识别公共地基，垂直切片用于尽早交付真实业务价值，两者结合而非互相替代。

拆解也是一次再审计。新发现的设计分歧、外部未知、资源不足和未来优化分别回到统一待决、验证、开工条件和后续候选，不为了让清单完整而自行补定结论。

**工作规划与开工授权必须分开。** 清单完成只说明可以怎样组织工作，不代表允许开工、付费调用、迁移、部署或使用真实账号。

### 执行方法

**1. 依赖分层：识别公共地基。** 前后置关系指向具体交付物，不能只用阶段名称表达依赖。

**2. 工作项画布：同页写清需求、边界、依据、依赖、验收和约束。** 无法填写验收或关键依赖的工作项，通常不具备继续细化条件。

**3. 两级拆解：规划级与执行级分开。** 只有当前批次且依赖成熟的工作项才拆成执行任务，避免全量过早细化。

**4. 垂直切片：尽早贯通真实主链路。** 共同地基稳定后，选择端到端且能证明业务价值的切片；切片包含真实状态、持久化和异常恢复，不用演示路径代替。

**5. 结构统一与体验优化分开验收。** 对既有页面，先保持已确认行为，统一代码结构并接通真实链路，再进行页面合并、系统代替人工操作、内容精简和布局优化。小任务可合并实施，但结构迁移、接口接入和交互 redesign 应分阶段验证，避免混改后无法归因。

**6. 缺口登记：问题回到对应权威位置。** 不在工作项中隐藏不确定性，也不另建重复问题台账。

**7. 授权门：分别确认范围、资源、环境、外部权限和验收责任。** 开工前检查当前批次范围和验收是否跨文档一致，核心交互与领域语义是否已对齐，关键外部能力是否有适配需求的候选及证据或验证安排。存在范围冲突、核心交互分歧、核心对象关系未决或关键技术路线无证据或验证安排时，相关工作项不得标为可开工；其他独立工作可继续。排期与实施均需明确授权，未授权的高影响操作不得提前执行。

**退出检查：** 每项工作有边界和验收，关键依赖无悬空，当前批次及衔接可以解释，新发现缺口已分流，规划和授权没有混同。

**最小有效产物：**

1. 规划级工作项清单及依赖；
2. 当前批次说明：目标、包含与不包含项、交接顺序、端到端验收和下一批入口；
3. 开工条件与授权事项；
4. 新发现问题的统一清单引用。

最重要的不是大任务表，而是说清：**现在做哪一批、为什么能做、如何衔接、怎样算完成。**

## 第五步：任务派发与执行反馈

把当前批次转化为执行者可以独立完成的任务，并用交付证据、独立审查和偏差处理证明任务真正完成。

**工作规划阶段确定可验证的工作项验收标准；对应技术细节可在开工前补齐。实施开始前，开工说明必须引用已确定的验收标准。** 开工说明使执行者不依赖原会话记忆也能工作，至少包含：任务身份与目标、所属工作项、执行边界、必读依据及章节、实施约束、环境与权限、验收标准和交付格式。

开工说明同时写明升级条件：需要改变需求或范围、方案存在实质冲突、必须修改公共契约、真实外部行为推翻假设、需要新增高影响权限，或验收标准本身不成立时，停止相关扩展并提交判断。

执行过程只保留有助于协作、排查和交接的信息，不写工具调用流水账。简单任务可以只有变更、测试和审查记录；复杂任务再增加交接说明。

交付后独立审查任务边界、需求与规范符合性、验收覆盖、关键实现、外部副作用、占位实现和文档一致性。测试环境可能掩盖真实行为时，应增加接近真实环境的验证。

执行反馈分四类处理：

- **实现偏离方案**：修实现并重新验证；
- **方案存在缺口**：回填方案并评估影响；
- **外部事实推翻假设**：保存证据，调整设计或默认行为并回归；
- **需求或范围变化**：说明原因、成本和验收影响，经确认后变更基线。

任务只有在交付、审查和必要回归完成后才能关闭。未完成事项、临时限制和遗留风险必须进入统一清单，并说明对后续工作的影响。

### 执行方法

**1. 开工单：把验收、边界和权限随任务下发。** 复杂任务分批交接，后续批次等待关键前置审查通过。

**2. 小步可证交付：每个交付都有对应证据。** 提供变更位置、自动化测试、运行结果和必要说明，不用大段描述代替证据，不留下无明确验收的占位实现。非破坏式重构先记录路由、功能、字段、关键交互和当前可运行基线，再逐步提取样例数据、接口边界、全局令牌、复用组件和状态管理，每步回归已确认行为。假数据只作为明确标注的样例、测试夹具或降级能力，真实接口接通后移除对应假成功路径。

**3. 独立审查：同时看测试和关键实现。** 重点检查权限、事务、并发、恢复和外部副作用；“有条件通过”必须写明条件、可用范围、限制和后续处理。

**4. 根因处理：失败先判断契约还是实现有误。** 不通过删除用例、放宽断言、吞掉异常或修改业务口径制造通过。

**5. 受控实测：外部验证单独设边界。** 涉及费用、账号、真实数据、外部写入或部署时，先明确授权、预算、输入、脱敏和停止条件；敏感配置和密钥不进入文档或代码库。

**6. 偏差分诊与回归：修正后验证影响面。** 改变默认行为、公共契约或核心模型后，重跑受影响范围，并更新交付记录和遗留项。

**退出检查：** 验收逐条有证据，独立审查完成，环境限制已说明，偏差正确归口，遗留项有后续责任，敏感信息未进入记录。

**最小有效产物：**

1. 任务开工说明；
2. 交付、测试证据与独立审查记录；
3. 必要的需求、方案、契约和验证更新；
4. 统一遗留事项及工作项状态；
5. 当前批次的轻量业务验收结论。

### 批次业务验收

技术任务关闭不等于业务目标达成。功能盘点和代码结构统一也不能直接证明初版可用。当前批次结束时，由目标角色或责任人复核核心场景：能否进入、取得真实数据、完成核心动作、保存或改变业务事实、重新进入后恢复，并处理失败和重复操作；最初的问题是否解决，哪些路径仍依赖降级或人工处理，是否引入新的使用成本，是否达到批次完成标准，下一批应继续、调整、暂停还是补验证。

验收记录只需保留已走通场景、未通过或受限场景、与原始目标的差距、继续使用条件和后续建议。可以并入工作规划的当前批次部分，不必为简单批次新建长报告。

需求按业务能力分组，技术方案划分服务与组件，工作规划组织可独立交付工作项，三者不一一对应。需求阶段不强定新建或完全复用，相关方案核实后由工作项引用；迭代范围引用需求编号，不复制正文。

## 四、产物的生命周期与收尾规则

| 产物 | 创建时机 | 更新条件 | 收尾方式 |
| --- | --- | --- | --- |
| 项目档案 | 第零步，按需补齐 | 背景、目标、本轮任务或有效约定变化 | 保留当前有效信息及来源 |
| 来源与资产索引 | 第零步，后续按需加深 | 新来源、位置变化或新增证据 | 保留导航、覆盖边界与调查入口 |
| 客户诉求清单 | 第一步 | 新诉求、澄清或处置变化 | 保留原意、出处与原因 |
| 统一语言 | 第一步，全程演进 | 概念澄清或语义变化 | 独立维护并同步引用 |
| 需求文档与基线 | 第一步 | 候选收敛，已确认要求经获批变更 | 保留当前基线与必要变更记录 |
| 方案与契约 | 第二步 | 审计回填、执行偏差、外部假设被推翻 | 保留当前有效方案 |
| 统一事项清单（待澄清、待决、冲突、待验证） | 全程 | 发现即登记，解决即关闭 | 结论回填正文，开放项保留，历史可归档 |
| 决策记录 | 按需 | 只追加 | 长期保留背景与权衡 |
| 工作规划 | 第四步 | 状态和批次变化 | 当前批次保留，历史批次归档 |
| 任务与交付记录 | 执行期 | 任务推进和关闭 | 保留证据索引，过程可归档 |
| 过程日志 | 按需 | 排查与交接需要 | 默认归档，不进入长期正文 |

关闭待澄清、待决、冲突或验证事项时，必须把结论写回诉求、统一语言、需求、方案、契约或工作项，清单只保留指针。否则清单会成为第二套事实源。

追溯由下游维护对上游依据的引用：诉求引用原始来源，需求引用诉求或约束，方案引用需求，工作项引用需求与方案，交付引用工作项与证据。通过引用反查承接和覆盖，不强制上游手工维护反向列表。

## 五、贯穿全程的八条原则

### 一、先对齐，再结论；先整体，再局部

讨论从整体理解开始，经分点澄清后回到整体结论，最后分点落实。整体未对齐不展开所有细节，局部结论未组合校验不视为完整方案。

### 二、单一事实来源

同一类信息只有一个权威来源，其他位置引用而不复述。术语进入统一语言，业务规则进入需求或方案，实体关系进入领域模型，重大权衡进入决策记录，待验证内容进入统一验证清单。重要结论不能只留在会话中。

### 三、证据分级

文档与静态检查、可运行原型、专项技术核验和真实场景验收的证明力不同。不能把设计合理当成已经验证，也不能把部分通过写成全部通过。

### 四、未核验，不承诺

依赖外部平台、供应商、性能或真实环境的能力，在取得证据前只能作为假设或候选方案，不能作为确定交付范围。

### 五、审查与决策分离

分析和审计负责说明问题、选项、代价和影响，最终结论由对应责任人作出。只有难以逆转、缺少背景容易令人意外且存在真实权衡的决定，才形成独立重大决策记录；普通结论进入正文。

### 六、统一语言持续对齐

审计、规划和执行中发现概念歧义或模型无法表达真实业务时，应回到统一语言或领域模型修正，再同步受影响内容。新术语不能由单个任务临时创造后自然扩散。

### 七、粒度随依赖收敛

依赖未定时保持较粗粒度，依赖明确后再细化。规划级用于范围和依赖，执行级用于当前实施，不以拆得最小为目标。

### 八、基线与授权分开管理

现状基线、需求文档中的确认基线、方案确认、工作规划和开工授权是不同决定。前一环节完成不自动意味着后一环节获批；已确认内容的修改必须留下原因、影响和批准记录。

## 结语

这套流程的关键不在于文档数量，而在于五个闭环：**现状能够支撑需求判断，需求能够追溯到方案，方案能够追溯到工作项，执行结果能够反过来校验方案，批次验收能够回答最初的问题是否真正解决。**

统一语言贯穿其中，默认推进与异常升级控制协作成本，最小有效产物保证信息值得长期保存。只要这些机制存在，具体使用什么文档、工具和项目管理系统都可以调整。
